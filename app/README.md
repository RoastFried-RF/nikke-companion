# 니케 컴패니언 오버레이 (app/)

Tauri v2 + Vue 3 + Vite + TypeScript로 만든 데스크톱 오버레이다(P-009 골격, P-010 계산 실행, P-011 게임 창 추적·화면 캡처,
P-016 계산 중단·활성화 없이 보이기·파일 고르기 창의 부모, P-019 요격전 화면 인식, P-017 요격전·성장 비교·티어 화면,
P-021 인식한 보스의 추천 자동 표시·중복 실행 방지, P-022 계정 받기 — 로그인 창·쿠키 붙여넣기, P-025 크롬 확장으로 계정 받기).

화면은 탭 다섯 개다(§화면(탭)):

- **추천·비교** — 계정 파일과 전투 조건 파일을 골라 **추천**(보유 니케에서 후보 생성)이나 **비교**(편성 파일)를 실행하고 순위를 그린다.
  이미 만들어 둔 비교 결과 JSON(`docs/data-model.md` §비교 결과)도 읽어 순위를 그린다.
- **요격전** — 계정과 보스 묶음 파일을 골라 보스별 편성 추천을 실행하고, 보스를 골라 그 보스의 상위 편성을 본다.
- **성장** — 계정·조건·기준 편성·업그레이드 후보 파일을 골라 성장 투자 비교를 실행한다.
- **티어** — `tier build`가 만든 결과 JSON을 불러와 등급표로 본다.
- **계정** — blablalink에서 내 계정의 육성 상태를 받아 계정 파일로 만든다: 쿠키 받기(크롬 확장 · 붙여넣기 · 앱 안의 로그인 창) →
  계정 새로 받기 → 변환·저장. 저장한 파일은 다른 화면의 계정 칸에 들어간다(§계정 받기). 권장하는 길은 **크롬 확장**이다 — 이미
  로그인된 브라우저에서 단추 한 번으로 끝까지 간다(§크롬 확장으로 계정 받기).

그 밖에:

- 니케 PC판 **게임 창**을 찾아 상태를 보이고, 지금 게임 화면을 PNG로 저장하고, 오버레이를 게임 창에 붙여 따라가게 한다
  (§게임 창·화면 캡처). 같은 캡처를 명령줄 도구 `nikke-capture`로도 한다.
- 캡처한 화면이 **이상 개체 요격전의 어느 화면인지, 어느 보스가 선택됐는지** 알아낸다(§화면 인식).
- **자동 추적**(기본 꺼짐): 켜 두면 게임 화면을 주기적으로 읽어, 게임에서 보고 있는 이상 개체 보스의 추천을 요격전 탭에
  스스로 보여 준다(§자동 추적). 게임은 읽기만 하고, 찍은 이미지는 저장하지도 화면에 넘기지도 않는다.
- 오버레이는 한 번만 뜬다 — 한 번 더 실행하면 두 번째는 조용히 끝나고 떠 있던 창이 보인다(§중복 실행 방지).

계산은 저장소 루트의 `src/core`(JS)가 웹뷰 안에서 그대로 한다 — Node CLI와 같은 코드다. 웹뷰에는 Node가 없으므로
엔진 프로세스 실행과 파일 읽기만 Rust 명령이 대신한다(`src/core/runtime.mjs`의 런타임 계약). Rust에는 계산 로직이 없다.

아직 하지 않는 것: 인식한 보스의 추천을 스스로 계산하기(결과가 없으면 "추천을 먼저 실행하라"고 알릴 뿐이다), 요격전 밖의
화면 인식, 유니온 레이드 화면(P-014 보류), 오버레이 안에서 티어 계산 돌리기(결과 파일만 읽는다).

**네트워크.** 오버레이 화면(웹뷰)과 이 앱의 Rust 코드는 네트워크 요청을 하지 않는다. 밖으로 나가는 것은 계정 탭에서 사용자가
시킬 때의 둘뿐이다: 「blablalink 로그인」으로 여는 **로그인 창**이 보여 주는 페이지(blablalink와 로그인 제공자)와, 「계정 새로
받기」가 실행하는 **엔진의 수집 스크립트**가 blablalink API에 하는 요청(§계정 받기).
들어오는 것을 받는 곳은 하나다: 계정 탭에서 「크롬 확장 연결」을 켰을 때만(기본 꺼짐) `127.0.0.1:47615`에서 듣는 **수신부** —
이 PC의 크롬 확장이 넘기는 쿠키를 받는다. 루프백에만 묶여 다른 PC에서는 닿을 수 없고, 밖으로 연결을 만들지 않는다
(§크롬 확장으로 계정 받기).

## 준비

- Node 20.19 이상, Rust(stable, MSVC 툴체인), WebView2 런타임(Windows 11에는 기본 설치)
- 계산 실행에는 Python 3.12와 엔진 서브모듈(`vendor/nikke-calc`)이 필요하다(§엔진 설정).
- 명령은 저장소 루트에서 `npm --prefix app …`로 실행하거나, `app/` 안에서 `npm …`로 실행한다.

```bash
npm --prefix app install
```

> `npm --prefix app install`을 루트에서 실행하면 npm이 루트 패키지를 `"nikke-companion": "file:.."`으로
> `app/package.json`에 적는다(npm 10의 `--prefix` 동작). 지워도 다음 설치 때 다시 생기므로 그대로 둔다.
> 앱 코드는 이 링크를 쓰지 않는다 — 루트의 계산 코드는 상대 경로 별칭 `@core`(= `../src/core`)로 가져온다.

## 개발 실행

```bash
npm --prefix app run tauri dev
```

Vite 개발 서버(`localhost:1420`, 이 PC 안에서만 열린다)와 오버레이 창이 함께 뜬다.
개발 실행에서는 앞서 불러온 파일이 없으면 경로 입력란에 샘플 결과(`app/tests/fixtures/compare.sample.json`)가
미리 채워지고 바로 불러온다.

개발 실행에서는 계산 실행 칸에도 샘플 입력(`data/samples/`의 검증용 계정·조건·편성)이 미리 채워진다.
`추천 실행`을 누르면 실제 엔진으로 계산한다(기본 예산 120건이면 2~3분, 샘플 계정은 87건). 진행 중에는 단계
(멤버 조합 → 배치), 끝난 건수, 쓴 예산, 경과 시간이 보인다.

다른 탭에도 개발 실행에서만 샘플이 채워진다: 요격전은 검증용 계정 + **실제 보스 묶음**(`data/intercept/anomaly.json`),
성장은 검증용 계정·조건·편성 + `data/samples/upgrades.sample.json`, 티어는 테스트 입력인
`app/tests/fixtures/tier.sample.json`(여덟 명만 계산한 결과 — 탭을 열면 바로 불러온다). 빌드한 실행 파일에서는 비어 있다.

다른 결과를 보려면 저장소 루트에서 결과 파일을 만들고 그 경로를 입력란에 넣는다(절대 경로 권장, 따옴표가 붙어 있어도 된다).

```bash
node src/cli.mjs compare --account data/samples/account.sample.json --condition data/samples/condition.solo-raid.json --squads data/samples/squads.sample.json --json 결과.json
```

마지막으로 불러온 경로는 기억했다가 다음 실행 때 다시 연다. 실행 인자로 줄 수도 있다: `nikke-companion.exe <결과.json>`.

## 화면(탭)

제목 줄·오버레이 상태·게임 창 칸 아래에 탭 다섯 개가 있다. 탭을 옮겨도 그 화면의 입력·결과·도는 계산은 남는다(화면을 내리지
않고 숨겨 둔다). 마지막으로 본 탭을 기억해 다음 실행 때 그 탭을 연다(실행 인자로 비교 결과 파일을 주면 추천·비교가 먼저다).
유니온 레이드 화면은 없다(P-014 보류).

| 탭 | 실행 | 결과 파일 불러오기 | 화면이 부르는 루트 함수 |
|---|---|---|---|
| 추천·비교 | 추천 · 비교 | `compare`·`suggest`의 `--json` | `suggestSquads` · `compareSquads` |
| 요격전 | 보스별 추천 | `intercept --json` | `recommendIntercept` |
| 성장 | 성장 투자 비교 | `growth --json` | `compareGrowth` |
| 티어 | (없음 — 읽기만) | `tier build --json` | (계산 없음. 상태 이름·판 번호는 `src/tier/evaluate.mjs`, 버스트 묶음은 `src/core/search.mjs`의 `burstOrderGroup`) |
| 계정 | 쿠키 받기 · 계정 새로 받기 | (없음) | `importProfile` · `importReport`(`src/core/import-profile.mjs` — CLI의 `import-profile`과 같은 변환) |

**계산 로직은 화면에 없다.** 실행은 `src/lib/compute.ts`가 파일을 읽어 루트의 함수에 런타임을 넘겨 부를 뿐이고(CLI와 같은 길),
화면은 결과 문서의 값을 서식만 입혀 그린다(`tests/contract.test.ts`가 확인한다). 앞의 화면 넷을 위해 새 Rust 명령이나 권한은
더하지 않았다 — 결과 파일은 기존 `read_json_file`로 읽는다. 그 뒤에 더한 명령은 자동 추적의 둘(§자동 추적)과 계정 받기의
아홉(§계정 받기 — 쿠키 파일·수집 프로세스·로그인 창을 다뤄야 해서)이다.

세 실행 화면(추천·비교, 요격전, 성장)이 함께 쓰는 것 — 같은 코드다(`src/lib/engineRun.ts`, `RunStatus.vue`, `RunButtons.vue`):

- **진행 표시**: `엔진 계산 중 — [보스 2/5(크라켄)] [1/2단계(멤버 조합)] 3/30건 끝남`과 막대, `예산 …건 중 …건`, 경과 시간.
  요격전은 보스마다 예산을 나눠 쓰므로 `이 보스의 예산 60건 중 30건`으로 보인다.
- **오류 표시**: `입력 오류 — …`(파일·옵션이 잘못됨), `실행 오류 — …`(엔진을 못 띄움·시간 초과), `<이름> 파일 — …`(파일을 못 읽음).
- **중단**: 도는 동안에만 `중단` 단추가 있고, 누르면 `중단됨 — 계산을 멈췄다. 결과는 계산 전 그대로다.`(§계산 중단).
- **한 번에 한 탭만 계산한다.** 엔진 배치 자리가 하나라서(Rust의 `BatchSlot`) 한 탭이 계산하는 동안 다른 탭의 실행 단추는 눌리지
  않는다. 계산하는 탭의 이름 옆에 점이 깜박인다. 탭을 옮겨도 계산은 계속되고, 티어 탭(읽기만)은 그동안에도 쓸 수 있다.

요격전·성장·티어 화면이 **잘못된 결과 파일**을 받으면 한국어 오류를 보이고 **앞서 보이던 화면을 그대로 둔다**
(`src/lib/reports.ts`가 `kind`와 `schema_version`, 그릴 때 기대하는 칸을 확인한다):

- 다른 종류: `티어 결과가 아니다 — 이 파일은 성장 비교 결과(kind: growth)다. 이 화면은 …이 만든 파일만 읽는다: <경로>`.
  편성 비교 결과(kind가 없다)를 넣으면 "추천·비교 탭에서 불러온다"고 알린다.
- 판이 다름: `schema_version이 맞지 않는다: 파일은 2, 이 화면이 읽는 판은 1이다: <경로>`.
- 못 읽음(없는 파일·JSON이 아님): Rust가 준 문장 그대로.

추천·비교 탭만 다르다: 결과 파일을 읽지 못하면 앞서 보이던 순위를 치운다(P-009 때의 동작 그대로 — 다른 파일의 순위로 오해하지
않게). 요격전·성장도 **다시 계산하는 동안과 계산이 실패한 뒤에 이전 결과를 남긴다**(`아래는 이전 결과다 — 새 계산이 끝나면 바뀐다`).
추천·비교는 계산을 시작하면 이전 순위를 치운다.

### 요격전

게임을 하면서 가장 자주 보는 화면이다. 결과가 있으면 입력 칸을 접어(`▸ 입력`으로 다시 편다) 위에서부터 이렇게 보인다 —
**보스 이름·약점 속성·1위 편성 5명은 접지 않은 상태에서 보인다**:

1. 계정 이름과 `검증용 데이터`·`검증용 보스 묶음` 표시, 계산 시각.
2. **보스 목록**(단추): 보스 이름과 약점 속성(속성 색). 누르면 그 보스가 아래에 보인다.
   속성 상성 미반영 보스에는 빨간 `!`, 미확인 값이 있는 보스에는 주황 `?`가 붙는다.
3. **고른 보스**: 이름, `약점 풍압`(유도한 값이면 `(속성에서 유도)`), `속성 철갑`(유도한 값이면 `(약점에서 유도)`).
   그 아래에 눈에 띄는 표시 — 빨간 `속성 상성 미반영`, 주황 `미확인 값 7칸 — 확정값이 아니다`.
4. **상위 편성**(기본 3개): 순위·총딜(단위 표기와 원값)·1위 대비·멤버별 딜(배치 순서 그대로). 보스의 약점 속성 니케에는
   `약점` 표시가 붙는다(결과의 `weak_pool.owned`).
5. 메모, `보상 … · 레벨 400(상한 400 — …) · 전투 180초(미확인 — 엔진 기본값)`, 탐색 요약, 접어 둔 `미확인 값 N칸 — 이렇게 계산했다`
   (칸마다 무엇으로 계산했는지), 접어 둔 `계산 정보`(콘텐츠·보스 값의 출처·엔진·캐시·보스별 예산·가정), 주의 문구(접지 않는다).

입력: 계정 파일, 보스 묶음 파일(`docs/data-model.md` §보스 묶음 — 이상 개체 요격전은 `data/intercept/anomaly.json`),
보스별 표시 수(빈 칸이면 3), 전체 시뮬 예산(빈 칸이면 300 — 보스 수로 나눈다. 기본 예산이면 몇 분 걸린다).
미확인 칸의 수에서 약점은 뺀다(계산 입력이 아니다 — CLI 표와 같다).

**기억하는 것**: 마지막으로 고른 보스(id)와 **마지막 결과 문서**. 앱을 다시 열면 그 결과와 그 보스가 바로 보이고
`앞서 본 결과를 다시 보였다(다시 계산하지 않았다)`고 알린다. 결과 문서는 이 PC의 웹뷰 저장소(localStorage — 경로를 기억하는
것과 같은 곳)에만 두고 저장소 폴더에는 쓰지 않는다. 계정 이름과 편성이 담긴다. 읽을 수 없는 판의 문서면 버리고, 저장하지
못하면(용량 등) 앞서 기억해 둔 옛 결과도 지운다. 기억해 둔 보스가 새 결과에 없으면 첫 보스를 보인다.
계정 파일이나 보스 묶음을 고친 뒤에는 다시 실행해야 한다 — 기억해 둔 결과는 그때의 입력으로 계산한 것이다.

**자동 추적**: 실행 칸 아래의 `자동 추적` 스위치를 켜 두면 게임에서 보고 있는 이상 개체 보스를 알아내 그 보스를 스스로
고른다(다른 탭을 보고 있었다면 요격전 탭으로 옮긴다). 추천 결과가 없으면 `추천을 먼저 실행하라`고 알릴 뿐 계산을 시작하지
않는다. 규칙·상태 표시·걸리는 시간은 §자동 추적.

### 성장

입력: 계정·전투 조건·편성 파일(기준 편성이 든 파일), 기준 편성 이름(비우면 파일의 첫 편성 — CLI의 `--squad`), 업그레이드 후보
파일(`data/samples/upgrades.sample.json` 형식). 계정·조건·편성 칸은 추천·비교에서 쓴 경로로 처음 채워진다.

결과: 기준 편성(이름·총딜·멤버별 딜), 업그레이드 후보의 순위(증가율 `+0.93%`, `총딜 34.63억 → 34.95억 (+3,210만)`, 바꾸는 육성
칸의 적용 전후 값, 딜이 달라진 멤버의 증가량), 계산하지 않은 후보와 사유, 엔진이 계산하지 못한 후보, 주의 문구.
총딜이 주는 후보는 빨갛게 적는다. 재화·비용은 없다(`compareGrowth`가 다루지 않는다).

### 티어

`node src/cli.mjs tier build … --json tier.json`이 만든 파일의 경로를 넣거나 `고르기`로 골라 `불러오기`를 누른다. 마지막으로 불러온
파일은 기억했다가 탭을 열 때 다시 읽는다. 이 화면은 계산하지 않는다(전원 계산은 시뮬 1,800건쯤이라 명령줄에서 돌린다).

- **임시 규칙 문구가 언제나 보인다**: `등급 규칙 <버전>은 임시다 — 대표 사례로 검증되지 않았다. 등급 경계는 바뀔 수 있다.`
  접히지 않고, 스크롤해도 맨 위에 붙어 있다. 결과 문서가 임시가 아니라고 밝힌 경우(`rules.provisional: false`)에만 내린다.
- 버전·조건: 엔진 커밋과 데이터 버전, 시나리오(보스·시간·육성 조건), 기준 편성 버전(몇 개 중 몇 개 사용)·등급 규칙 버전·방법,
  시뮬 횟수, 캐시, 계산 시각. 접어 둔 것: 가정, 등급 경계, 기준 편성(멤버·총딜, 쓰지 못했으면 사유).
- **버스트 단계 필터**: `전체 · 1단계 · 2단계 · 3단계`(결과에 있는 단계만, 인원 수와 함께). 전 단계(A) 니케는 3단계 묶음이다.
- **status별로 다르게 그린다**:
  - `예측 평가` — 등급별 묶음(규칙 문서의 등급 순서, 해당 니케가 없는 등급은 그리지 않는다) 안에 순위·이름·버스트 단계·
    점수(소수 셋째 자리)·파란 `예측 평가` 표시. 줄을 누르면 점수가 나온 자리(`<기준 편성>의 <멤버> 자리: 38.12억 → 45.06억`),
    다른 자리의 점수, 메모가 펴진다.
  - `평가 보류` — 등급 표와 **따로 묶는다**(`평가 보류 — 등급 없음 — 0점이 아니다`). 주황 `평가 보류(사유)` 표시와 사유 문장.
    점수와 순위는 없다.
  - 그 밖의 상태(앞으로 더해질 `실측 대조 완료` 등) — 등급이 있으면 등급 묶음에, 예측 평가와 다른 색의 표시로.
- **미지원 효과 표시가 있는 항목은 눈에 띈다**: 접지 않은 줄에 빨간 `미지원 효과 있음`이 붙고 줄 전체에 빨간 테두리가 생긴다.
  (지금 엔진·시나리오에서는 그 경고가 실제로 나오지 않는다 — 테스트는 샘플을 복사해 바꾼 결과로 본다.)
- 주의 문구는 접지 않는다.

## 계산 실행

아래는 추천·비교 탭의 설명이다. 진행 표시·오류 표시·중단은 요격전·성장 탭도 같다(§화면(탭)).

| 방식 | 입력 | 하는 일 |
|---|---|---|
| 추천 | 계정 파일, 전투 조건 파일, (선택) 후보 수·표시 수·예산, 배치 탐색 켬/끔 | 보유 니케에서 후보 편성을 만들어 엔진으로 비교하고(1단계), 상위 조합의 배치 순서를 바꿔 다시 계산해(2단계) 상위만 보인다 (`node src/cli.mjs suggest`와 같다) |
| 비교 | 계정 파일, 전투 조건 파일, 편성 파일 | 편성 파일의 편성을 엔진으로 비교한다 (`node src/cli.mjs compare`와 같다) |

- 추천의 **예산**은 엔진 시뮬 횟수의 상한이다(두 단계를 합쳐서, 빈 칸이면 120). **배치 탐색**을 끄면 조합마다 배치
  하나만 계산한다(CLI의 `--no-refine`). 규칙과 근거는 `docs/data-model.md` §배치 탐색 — 화면에는 규칙이 없고
  루트의 `suggestSquads`가 정한다. 계산 중에는 `1/2단계(멤버 조합) 3/30건 끝남 · 예산 120건 중 30건`처럼 보이고,
  결과에는 `탐색: 시뮬 87건 / 예산 120건 (…)` 줄과 조합별 `배치 탐색: …` 메모가 보인다. 예산이 모자라 못 본
  후보·배치 변형의 수는 그 줄과 주의 문구에 적힌다.

- 파일은 `고르기`로 고르거나 경로를 직접 넣는다(따옴표가 붙어 있어도 된다). 쓴 경로와 방식은 기억한다.
- 입력이 잘못되면 `입력 오류 — …`, 엔진을 띄우지 못하거나 시간이 넘으면 `실행 오류 — …`로 보인다.
  엔진이 일부 편성에서만 오류를 내면 그 편성은 "실패한 편성"으로 보이고 나머지는 순위에 남는다.
- 계산 중에는 다시 실행하거나 결과 파일을 불러올 수 없다. 멈추려면 **중단** 단추를 누른다(§계산 중단).
- 같은 엔진 판·같은 요청은 다시 계산하지 않는다(시뮬 결과 캐시, `docs/data-model.md` §시뮬 결과 캐시). 이 앱은
  **메모리 저장소만** 쓴다 — 앱이 켜져 있는 동안만 남고 파일에 쓰지 않으며, CLI의 `data/cache/sim/`과 나눠 쓰지 않는다.
  결과 화면의 `캐시: 적중 N건 · 엔진 계산 N건 · 새로 저장 N건` 줄로 보인다. 진행 건수는 엔진에 보낸 요청만 센다
  (모두 적중하면 엔진을 부르지 않고 곧바로 끝난다). 엔진 커밋을 모르거나 엔진 폴더에 커밋하지 않은 변경이 있으면
  캐시를 쓰지 않고 그 이유가 같은 자리에 보인다.

### 계산 중단

계산이 도는 동안에만 실행 단추 옆에 **중단** 단추가 보인다. 누르면:

1. Rust 명령 `engine_cancel`이 도는 배치의 엔진 프로세스를 모두 끝낸다. 배치 호출(`engine_run_batch`)은
   `중단됨: 엔진 계산을 멈췄다` 오류로 돌아온다. 그때까지 끝난 줄은 버린다(일부만 계산된 배치를 결과로 내지 않는다).
2. 화면은 오류가 아니라 **`중단됨 — 계산을 멈췄다. 결과는 계산 전 그대로다.`**를 보이고, 계산을 시작하기 전에 보이던
   결과(순위)를 그대로 다시 보인다. 이전 결과가 없었으면 결과 없이 `중단됨`만 보인다.
3. 바로 다시 실행할 수 있다. 다시 실행하면 `중단됨` 줄은 사라진다.

알아 둘 것:

- **누른 뒤의 화면은 언제나 `중단됨`이다.** 엔진이 돌지 않는 순간(파일 읽기, 두 단계 사이의 캐시 확인)에 눌렀으면 멈출
  프로세스가 없으므로 다음 배치를 엔진에 보내지 않고 끝낸다. 누른 순간에 계산이 마침 끝났어도 그 결과는 쓰지 않는다.
- 멈춘 배치의 결과는 시뮬 결과 캐시에 남지 않는다. 앞 단계(추천의 1단계)가 이미 끝났으면 그 결과는 캐시에 있어, 다시
  실행하면 그 단계는 엔진을 부르지 않는다.
- 엔진 프로세스는 Windows의 **Job Object**로 묶어 끝낸다(`src-tauri/src/engine_win32.rs`). 띄운 `python`만 끝내면
  그 `python`이 띄운 프로세스(가상 환경의 실행기가 띄운 진짜 python, 엔진이 부르는 `git`)가 남을 수 있고, 남은 프로세스가
  엔진의 출력 파이프를 쥐고 있어 호출이 돌아오지 않는다(가짜 엔진으로 확인: Job 없이는 300초 동안 돌아오지 않았다).
  시간 초과·다른 프로세스의 오류로 멈출 때도 같은 길이다. 다루는 것은 이 앱이 띄운 프로세스뿐이다.
  Windows가 아니면 띄운 프로세스 하나만 끝낸다.
- 한계: 프로세스를 띄운 직후에 Job에 넣으므로, 그 사이(마이크로초)에 만들어진 자식은 Job 밖이다.
  (앱이 끝나거나 죽을 때 돌던 엔진 프로세스가 남던 문제는 P-024에서 고쳤다 — 아래 §종료 시 정리.)
- 중단 명령이 배치 호출보다 먼저 Rust에 닿으면 Rust는 "도는 배치 없음"(false)으로 답하고 아무것도 멈추지 않는다
  (다음 배치를 미리 멈추지 않는다). 화면은 그 배치가 돌아올 때까지 0.1초마다 다시 청한다.

돌려 본 결과(2026-11-12, `tests/engine_cancel.rs`): 실제 엔진으로 40건(프로세스 4개)을 시작해 4건이 끝난 시점에 멈추니
중단을 청한 뒤 약 0.01초에 `중단됨`으로 돌아왔고, 그때 떠 있던 python 4개와 콘솔 호스트가 모두 사라졌다. 같은 자리로 다시
실행한 배치는 끝까지 돌았다. **오버레이 창에서 단추를 눌러 본 것은 아니다** — 화면 흐름은 가짜 엔진 테스트로만 확인했다.

### 종료 시 정리

계산이나 계정 수집이 도는 중에 앱이 끝나면, 돌던 엔진 프로세스(`python -m runner.sim`)와 수집 스크립트
(`scraper/profile_fetch.py`)가 **그 자식 프로세스까지** 함께 끝난다(P-024 — 예전에는 배치를 마칠 때까지 남았다). 두 겹이다:

1. **앱이 끝나는 길에서 멈춘다.** 끝내기 단추(`quit_app`)와 오버레이 창 닫기(Alt+F4 등 — 오버레이 창이 닫히면 로그인 창이 떠
   있어도 앱을 끝낸다) 모두 앱의 종료 이벤트를 지나고, 거기서 `stop_running_work`가 엔진 배치와 계정 수집의 자리(`BatchSlot`)에
   멈추라고 한 뒤 둘 다 끝날 때까지 최대 3초 기다린다(`engine::stop_all_and_wait` — 중단 단추와 같은 길로 프로세스 묶음을 끝낸다).
   도는 일이 없으면 기다리지 않는다.
2. **프로세스 묶음이 앱과 함께 닫힌다.** 엔진·수집 프로세스를 넣는 Job Object에 「닫히면 안의 프로세스를 모두 끝낸다」
   (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)를 걸었다(`src-tauri/src/engine_win32.rs`). Job의 핸들은 이 앱만 쥐고 있으므로 앱이
   **어떻게 끝나든** — 작업 관리자의 프로세스 종료, 충돌, 1번이 시간 안에 못 끝낸 경우 — Windows가 핸들을 닫으면서 끝낸다.
   Windows가 아니면 1번만 있다.

알아 둘 것: 이 설정 때문에 계산이 **정상으로 끝났을 때에도** 엔진이 남겨 둔 자식 프로세스가 있으면 묶음을 버릴 때 함께 끝난다
(엔진은 그런 프로세스를 남기지 않는다 — 계산 결과에는 영향이 없다). `windows` 크레이트의 그 구조체는 다른 프로세스를 여는 호출이
딸린 기능(`Win32_System_Threading`)을 켜야 나와서, 켜지 않고 같은 모양을 직접 적었다(크기를 단위 테스트가 확인한다).

확인(`tests/exit_cleanup.rs` — 평소 `cargo test`에서 돈다. python이 필요하다): 이 테스트 실행 파일을 한 번 더 띄워 「앱」 노릇을
시킨다 — 앱의 명령이 부르는 함수 그대로 가짜 엔진 둘과 가짜 수집 스크립트를 돌리고, 셋 다 자식 프로세스를 하나씩 더 띄운 채 멈춰
있다(python 여섯 개). 그 실행 파일을 세 가지로 끝낸 뒤 시스템 프로세스 목록에서 그 자손이 5초 안에 사라지는지 본다:

| 끝나는 방식 | 무엇을 보는가 | 잰 값(2026-11-12) |
|---|---|---|
| 밖에서 끝냈다(`TerminateProcess` — 작업 관리자의 프로세스 종료와 같다) | 2번만으로 끝난다 | 약 0.07초 |
| 아무 정리 없이 스스로 끝났다 | 2번만으로 끝난다 | 약 0.07초 |
| 앱이 끝나는 길(`stop_all_and_wait` 뒤 종료) | 1번이 시간 안에 끝났다고 답하고, 남지 않는다 | 약 0.1초 |

「닫히면 끝낸다」 설정을 빼고 돌리면 앞의 두 건이 `자식 프로세스가 남아 있다`(python 여섯 개)로 실패하는 것을 확인했다.
**실제 오버레이 창에서 계산 중에 끝내 본 것은 아니다** — 종료 이벤트에서 `stop_running_work`가 불리는 것은 계약 테스트(코드 읽기)
까지다(§사람이 확인할 것).

### 엔진 설정

엔진 폴더와 python 경로는 화면에서 바꿀 수 없다(화면이 실행할 프로그램을 정하지 못하게). 우선순위:

1. 환경 변수 `NIKKE_ENGINE_DIR`, `NIKKE_PYTHON`
2. 설정 파일 `%APPDATA%\local.nikke-companion.overlay\settings.json`
3. 기본값: 실행 파일·현재 폴더에서 위로 올라가며 찾은 `vendor/nikke-calc`, PATH의 `python`

```json
{ "engine_dir": "E:\\code\\nikke-companion\\vendor\\nikke-calc", "python": "python", "concurrency": 4, "timeout_seconds": 600 }
```

모든 칸은 선택이다. `concurrency`는 동시에 띄울 엔진 프로세스 수(1~4, 기본은 코어 수 − 1을 4로 제한),
`timeout_seconds`는 엔진 프로세스 하나의 시간 제한(기본 600초)이다. 저장소 안에서 빌드한 실행 파일은 설정 없이 돈다.

## 게임 창·화면 캡처

### 게임은 읽기만 한다

이 앱은 게임 창을 옮기거나 크기를 바꾸거나 앞으로 가져오지 않고, 게임에 마우스·키 입력이나 창 메시지를 보내지 않고,
게임 프로세스를 열거나 메모리를 읽거나 무엇을 주입하지 않는다(`docs/spec.md` §게임과의 상호작용 규칙).
쓰는 것은 표준 창 API뿐이다: 창 열거와 창 속성 읽기, DWM 창 경계, 시스템 프로세스 목록(이름만 — 게임 프로세스의 핸들을
열지 않는다), Windows.Graphics.Capture. 붙이기가 옮기는 것은 오버레이 창뿐이고, 게임 위에 머물기(§게임 위에 머물기)가 창 순서를
올리는 것도 오버레이 창뿐이다 — 게임 창에 대해서는 「누가 위인가」를 읽기만 한다. `tests/contract.test.ts`가 Rust 코드에
게임 창을 움직이거나 입력을 보내거나 프로세스를 여는 호출이 없는지, 창 순서를 바꾸는 호출이 오버레이 창 모듈의 한 곳에만 있는지 확인한다.

### 게임 창 찾기

1. 최상위 창을 열거해 후보를 모은다: 프로세스가 `nikke.exe`·`nikke_launcher.exe`이거나 제목이 `NIKKE`인 창.
2. 게임 창은 **`nikke.exe`의 창**이고, 보이고(WS_VISIBLE), DWM이 가리지 않았고, 화면 영역이 있는 창이다.
   런처(`nikke_launcher.exe`)는 제목이 같아도 게임이 아니다. 최소화된 창은 게임 창으로 보고 상태를 "최소화"로 알린다.
3. 여러 개면 제목이 `NIKKE`인 것 → 최소화되지 않은 것 → 화면 영역이 넓은 것 → 핸들 값이 작은 것.

규칙은 `src-tauri/src/game_window.rs`의 순수 함수(`select_game_window`)이고 Win32 호출은 `game_win32.rs`에만 있다.
창 정보의 좌표와 크기는 모두 **물리 픽셀**이다: `client`(제목 표시줄·테두리를 뺀 게임 화면 영역의 화면 좌표와 크기),
`frame`(창에서 보이는 부분 전체), `minimized`, `foreground`(전경 창인가), `scale_factor`(창이 놓인 모니터의 배율).

### 오버레이에서

- **게임 창** 칸이 상태(찾음/없음/최소화됨/런처만)와 화면 영역의 크기·배율을 보인다. 게임 창을 찾은 뒤에는 0.1초마다(오버레이를
  숨겼거나 게임이 없으면 1초마다) 다시 읽는다 — §게임 위에 머물기.
- **화면 저장** 단추나 전역 단축키 `Alt+Shift+S`가 지금 게임 화면을 저장하고, 저장한 경로(또는 한국어 오류)를 칸에 알린다.
  단추는 게임 창을 찾았을 때만 눌린다. 단축키는 언제나 듣고, 못 찍으면 이유를 알린다.
- **게임 창에 붙이기**를 켜면 오버레이가 게임 화면 영역의 오른쪽 위 안쪽(가장자리에서 12px)에 자리 잡고, 게임 창이 움직이거나
  크기가 바뀌면 따라간다(0.05초마다 게임 창 위치를 읽는다). 끄면 그 자리에 머문다. 켜 둔 것은 기억했다가 다음 실행 때 다시 켠다.
  - 게임 창이 가만히 있는 동안 오버레이를 끌어 옮기면 그 자리에 머물고, 게임 창이 다시 움직이면 오른쪽 위로 돌아간다.
  - 게임이 없거나 최소화돼 있으면 옮기지 않고 그 자리에서 기다린다(붙이기는 켜진 채다) — 게임 창이 다시 뜨면 새로 붙는다.
    다른 모니터로 간 게임 창도 따라간다(§게임 위에 머물기 §붙이기의 가장자리 처리). 오버레이가 게임 화면보다 넓으면 게임 화면의
    왼쪽 끝에 맞춘다.
  - 붙이면 오버레이가 게임 화면 안쪽에 놓인다 — 게임을 눌러도 가려지지 않게 오버레이가 자기 창을 다시 올린다(§게임 위에 머물기).
  - 위치 계산은 순수 함수다(`game_window.rs`의 `attach_position`·`follow_target`·`follow_step`).

### 저장하는 곳

캡처 이미지는 계정 정보와 게임 화면을 담는다. **저장소에 올리지 않는다** — 기본 폴더 `data/captures/`는 gitignore에 있다.

- 폴더: 환경 변수 `NIKKE_CAPTURE_DIR` → 저장소의 `data/captures`(실행 파일·현재 폴더에서 위로 올라가며 저장소를 찾는다).
  저장소 밖에서 실행해 폴더를 정할 수 없으면 저장하지 않고 알린다. 화면(웹뷰)은 폴더를 정하지 못한다.
- 파일 이름: `<현지 시각 YYYYMMDD-HHMMSS-mmm>[_<라벨>].png`. 라벨은 글자·숫자(한글 포함)·`-`·`_`만 남기고(공백은 `-`,
  경로 구분자·점·따옴표 등은 버림) 48자로 자른다. 같은 이름이 있으면 덮어쓰지 않고 `-2`, `-3`…을 붙인다.
- 형식: 8비트 RGB PNG, 클라이언트 영역의 원본 해상도 그대로.

### 명령줄 도구 `nikke-capture`

저장소 루트에서:

```bash
cargo run --quiet --manifest-path app/src-tauri/Cargo.toml --bin nikke-capture -- --info
cargo run --quiet --manifest-path app/src-tauri/Cargo.toml --bin nikke-capture -- --name lobby
cargo run --quiet --manifest-path app/src-tauri/Cargo.toml --bin nikke-capture -- --out D:\shots --name "솔로 레이드"
```

| 인자 | 하는 일 |
|---|---|
| `--info` | 게임 창 정보를 JSON 한 줄로 출력: `{hwnd, pid, process_name, title, client, frame, minimized, foreground, scale_factor}` |
| (없음) / `--out <폴더>` / `--name <라벨>` | 게임 화면을 저장하고 `{path, width, height, captured_at, method, window}`를 JSON 한 줄로 출력. `--out`이 없으면 기본 폴더. `method`는 캡처 방식(지금은 `wgc`뿐) |
| `--recognize <PNG 파일>` | 저장해 둔 캡처에서 화면 종류와 보스를 알아내 `{screen, boss, confidence, evidence, width, height}`를 JSON 한 줄로 출력(§화면 인식). 게임이 없어도 된다 |
| `--recognize-live` | 게임 창을 찍어 인식만 하고 같은 JSON을 출력. **이미지는 저장하지 않는다** |
| `--help` | 사용법 |

종료 코드: `0` 성공 · `1` 인자 오류·최소화·캡처/저장 실패·이미지 읽기 실패 · `2` 게임 창 없음(게임이 꺼져 있거나 런처만 떠 있다).
인식 결과가 `unknown`이어도 종료 코드는 0이다(인식은 끝났고 답이 "모른다"이다). 한 번에 한 가지만 한다 — `--info`·`--recognize`·
`--recognize-live`는 서로, 그리고 `--out`·`--name`과 함께 쓸 수 없다.
오류는 표준 오류에 한국어로 나온다. `captured_at`은 UTC(ISO 8601), 파일 이름의 시각은 현지 시각이다.
최소화된 게임 창에 `--info`를 하면 `minimized: true`와 크기 0의 `client`가 나오고 종료 코드는 0이다.

### 캡처 방식 — Windows.Graphics.Capture

`windows` 크레이트(0.62 — Tauri가 이미 끌어오는 판이라 새 의존성이 아니다. 기능만 더 켰다)로
**Windows.Graphics.Capture(WGC)**를 직접 부른다: 게임 창으로 캡처 대상을 만들고(`IGraphicsCaptureItemInterop::CreateForWindow`),
프레임 하나를 받아 클라이언트 영역만 CPU 메모리로 읽은 뒤 세션을 닫는다. 받은 표면은 창 전체(제목 표시줄·테두리 포함)라서
프레임을 받은 시점의 DWM 창 경계와 클라이언트 영역의 화면 좌표로 잘라 낼 자리를 계산한다(`capture.rs`의 `client_crop`).

고른 이유:

- **가려져도 찍힌다.** WGC는 화면에 보이는 것이 아니라 합성기(DWM)가 가진 그 창의 화면을 넘겨준다(화면을 그대로 복사하는
  BitBlt는 가린 창이 찍힌다). 테스트의 자기 창으로는 확인했다(`live_capture.rs` — 가린 자리에 가리개 색 픽셀 0개).
  게임 창으로 같은 것을 보는 테스트는 `live_game.rs`에 있다 — 통과 여부는 아래 §실제 게임 테스트의 "돌려 본 결과"를 보라.
- **게임에 아무것도 보내지 않는다.** PrintWindow는 대상 창에 그리기 요청이 갈 수 있다. WGC는 합성기 쪽에서 끝난다.
- **Direct3D로 그리는 창도 찍힌다.** 니케(Unity)에서 실제로 찍혔다(2026-11-12, 창 모드 2212×1244, 전경이 아닌 상태).
- **PrintWindow는 니케 창에서 실패했고, 코드에서 뺐다.** 개발 중에 `PrintWindow(PW_CLIENTONLY | PW_RENDERFULLCONTENT)`를
  한 번 불러 봤는데 FALSE를 돌려줬다(원인은 확인하지 않았다). 그 시험을 한 뒤 몇 분 사이에 게임 창이 최소화돼 있었다 —
  사용자가 한 것인지 그 호출과 관계가 있는지 확인하지 못했다(그 앞의 WGC 캡처 직후에는 최소화돼 있지 않았다). 쓸 수 없고
  영향도 모르는 호출이라 남기지 않았다. BitBlt도 넣지 않았다. `tests/contract.test.ts`가 이 호출들이 없는지 확인한다.
- 래퍼 크레이트(`windows-capture`, `xcap` 등)는 쓰지 않았다. 필요한 것이 프레임 한 장이라 직접 부르는 코드가 짧고,
  의존성이 늘지 않는다.

확인한 문서와 확인하지 못한 문서: Microsoft Learn의 "Screen capture"(WGC 개요 — 노란 테두리, `IsSupported`, 프레임 풀과
`ContentSize`)를 읽었다. docs.rs의 크레이트 문서(`windows` 0.62.2, `windows-capture`, `xcap`)는 이 작업을 한 세션에서 열 수
없었다(웹 읽기 권한 없음) — `windows` API의 이름과 인자는 컴파일과 실제 게임 실행으로 확인했고, 래퍼 크레이트는 문서를
보지 못한 채로 비교했다(위 이유는 문서가 아니라 필요한 기능의 크기로 판단한 것이다).

한계:

- **최소화된 창은 찍지 못한다.** 한국어 오류로 알리고, 창을 복원하지 않는다(게임 창을 건드리지 않는다).
- **빈 화면은 저장하지 않는다.** 네 모서리를 뺀 모든 픽셀이 같은 색(전부 검은 화면 포함)이면 최대 0.7초 동안 다음 프레임을
  더 받아 보고, 그래도 같으면 오류로 돌려준다. 그래서 정말로 한 색인 게임 화면(검은 로딩 화면)도 저장되지 않는다.
- **창 모드에서는 아래쪽 두 모서리가 검게 찍힌다.** Windows 11이 창 모서리를 둥글게 깎기 때문이다(반지름 8px × 배율 —
  화면에서는 그 자리에 뒤의 창이 보인다). 클라이언트 영역의 아래쪽 모서리가 창 모서리와 겹쳐, 깎인 바깥쪽 몇 픽셀은
  `(0, 0, 0)`으로, 둥근 테두리 선이 지나는 픽셀은 테두리 색으로 온다(`live_capture.rs`의 자기 창과 2026-11-12에 찍은 실제
  게임 캡처 2212×1244에서 확인 — 맨 아래 모서리 픽셀이 `(0, 0, 0)`, 그 대각선 안쪽 픽셀이 `(34, 34, 34)`). 이미지는 그대로 저장한다 — 화면 인식에서 모서리 몇 픽셀은 믿지 말 것. 이 픽셀 때문에
  한 색 화면이 정상으로 판정되던 것을 고쳤다: 빈 화면 판정은 네 모서리의 24×24픽셀(작은 프레임에서는 변의 1/4)을 보지 않는다.
- **전체 화면은 확인하지 않았다.** 테두리 없는 창 모드는 될 것으로 보지만(창 경계와 클라이언트 영역이 같아진다) 돌려 보지
  않았고, 전용 전체 화면에서는 프레임이 오지 않거나 검게 나올 수 있다.
- **캡처하는 순간 노란 테두리가 보일 수 있다.** 테두리를 빼 달라고 요청하지만(`IsBorderRequired = false`, Windows 11) 요청이
  받아들여졌는지는 확인하지 않는다. 테두리는 이미지에는 찍히지 않는다. 마우스 커서도 빼 달라고 요청한다.
- **창이 움직이는 중이면 실패할 수 있다.** 받은 표면에서 클라이언트 영역이 벗어나거나 크기가 달라지면 잘린 이미지를 만들지
  않고 "크기가 다르다" 오류로 돌려준다. 다시 찍으면 된다.
- **HDR**: 프레임을 8비트 BGRA로 받는다. HDR 화면에서 색이 어떻게 바뀌는지는 확인하지 않았다.
- Windows 10 1903 이전에는 WGC가 없다(오류로 알린다). 프레임은 최대 2.5초 기다린다.
- **Direct3D 장치와 캡처 대상은 한 번 만들어 다시 쓴다**(P-021 — 처음에는 캡처마다 전부 새로 만들었고 한 번에 약 200ms가
  걸렸다. 지금은 첫 캡처 약 250ms, 그 뒤 약 20ms — 잰 값과 그렇게 바꾼 이유는 §자동 추적 §걸리는 시간). 프레임 풀과 세션은
  캡처마다 새로 만들고 닫는다 — 찍지 않는 동안에는 캡처가 돌지 않는다. 다시 쓰는 것은 프로세스가 끝날 때까지 들고 있다
  (자동 추적을 꺼도 놓지 않는다). 캡처 API가 실패하면 둘 다 버리고 다음 캡처에서 새로 만들고, 그 밖의 실패(빈 화면·크기
  불일치)에서는 캡처 대상만 새로 만든다. 다른 창을 찍게 되면(게임을 껐다 켬) 캡처 대상을 새로 만든다.

### 실제 게임 테스트

```bash
cargo test --manifest-path app/src-tauri/Cargo.toml --test live_game -- --ignored
```

`tests/live_game.rs`는 실행 중인 니케가 필요해서 `#[ignore]`다(평소 `cargo test`에서는 건너뛴다). 게임 창이 **떠 있어야**
한다 — 최소화돼 있으면 실패한다(테스트도 게임 창을 복원하지 않는다). 확인하는 것:

- 게임 창을 찾는다(`nikke.exe`, 런처가 아니다). 클라이언트 영역이 창 경계 안에 있고 배율이 읽힌다.
- 캡처한 이미지의 크기가 클라이언트 영역과 같고 빈 화면·거의 검은 화면이 아니다.
- 캡처·저장 전후로 게임 창의 핸들·위치·크기·최소화 여부·전경 여부가 같다.
- 게임 화면 가운데를 이 테스트의 작은 자홍색 창(항상 위, 비활성)으로 **가린 채** 찍어도 그 색이 찍히지 않는다.
  가리개가 실제로 화면에 보이는지는 화면 픽셀로 확인한다. 테스트 중 1초쯤 게임 화면 가운데에 자홍색 네모가 보인다.
- `nikke-capture --info`와 캡처 저장(종료 코드 0, JSON 한 줄, PNG 크기).

테스트가 쓴 캡처는 `data/captures/_live-test-…` 폴더에 두었다가 끝나면 지운다.

돌려 본 결과(2026-11-12, P-011을 만든 세션):

- 명령줄 도구로 실제 게임을 한 번 찍었다: 창 모드 2212×1244, 전경이 아닌 창. 저장된 PNG를 열어 보니 제목 표시줄·테두리
  없이 로비 화면 전체가 찍혀 있었다. 그때 다른 창이 게임을 가리고 있었는지는 모른다.
- 그 뒤 게임 창이 최소화됐고 세션이 끝날 때까지 그대로였다. 그래서 **`live_game.rs`의 다섯 테스트는 최소화 상태에서만 돌았고
  모두 "게임 창이 최소화돼 있다"로 실패했다** — 가려진 창 캡처, 캡처 전후 창 상태 비교는 아직 통과를 확인하지 못했다.
- 최소화 상태에서 확인한 것: `--info`가 `minimized: true`를 내고(종료 코드 0), 캡처는 한국어 오류와 종료 코드 1로 끝나고,
  오버레이의 게임 창 칸이 "최소화됨"을 보이고 저장 단추가 막히고, 붙이기를 켜도 오버레이가 그 자리에 머문다.
- 두 번째 세션(같은 날 06:07~)에서도 게임 창은 계속 최소화돼 있었다. 그때 화면의 전경 창은 다른 프로그램이었고 이 앱의
  프로세스는 떠 있지 않았다. 누가 최소화했는지는 여전히 모른다. `live_game.rs`는 이번에도 돌리지 못했다.

### 게임 없이 캡처 경로 확인

```bash
cargo test --manifest-path app/src-tauri/Cargo.toml --test live_capture -- --ignored
```

`tests/live_capture.rs`는 게임 대신 **테스트가 띄운 자기 창**(제목 표시줄·테두리가 있는 보통 창, 네 구역을 다른 색으로 칠함)을
같은 캡처 함수로 찍는다. 게임이 꺼져 있거나 최소화돼 있어도 돌고, 게임 창은 읽지도 건드리지도 않는다. 화면이 켜진
데스크톱이 필요해서 `#[ignore]`다. 1~2초 동안 화면 왼쪽 위에 작은 창과 자홍색 네모가 떴다 사라진다(활성화하지 않는다).

- 클라이언트 영역만 정확히 잘라 낸다: 각 구역의 맨 바깥 행·열이 그 구역의 색이다(한 픽셀이라도 밀리면 테두리가 섞인다).
- 가운데를 다른 창으로 가린 채 찍어도 가리개의 색이 한 픽셀도 찍히지 않는다(가리개가 화면에 보이는지는 화면 픽셀로 확인).
- 한 색으로만 칠한 창은 `BlankFrame` 오류다(실제 WGC 프레임으로 — 둥근 모서리의 검은 픽셀이 있어도).
- 최소화한 창은 `Minimized` 오류이고 캡처를 시도해도 최소화된 그대로다. 다시 띄우면 같은 크기로 찍힌다.
- 캡처 전후로 대상 창의 위치·크기·최소화·전경 여부가 같다.

돌려 본 결과(2026-11-12, Windows 11 26300, 배율 100%): 네 테스트 통과. 처음 돌렸을 때는 한 색 창이 성공으로 돌아와
실패했다 — 위 §한계의 둥근 모서리 문제를 여기서 찾아 고쳤다. **이것은 게임 창으로 한 확인이 아니다**: 니케(Direct3D로 그리는
창)가 가려졌을 때 어떻게 찍히는지, 캡처가 게임 창 상태를 바꾸지 않는지는 `live_game.rs`가 통과해야 확인된다.

## 게임 위에 머물기

사용자가 알린 문제(2026-11-12): 「게임 창에 붙이기」를 켠 뒤 게임을 움직이면 오버레이가 게임 뒤로 가서 보이지 않는다.

**원인.** 니케 게임 창은 그 자체가 항상 위 창이다(확장 스타일 `0x00000108` — `WS_EX_TOPMOST`가 들어 있다). 항상 위 창끼리는
나중에 활성화된 창이 위로 온다. 게임을 누르거나 옮기면 게임이 오버레이를 덮고, 붙이기는 오버레이를 게임 화면 **안쪽**에 두므로
통째로 가려진다.

**고친 방법(P-024).** 게임 창이 오버레이보다 위로 올라온 것을 보면 오버레이가 **자기 창**을 활성화 없이 다시 맨 위로 올린다.
붙이기를 켜지 않아도 적용한다.

- 게임 창 추적 스레드(`game-tracker`)가 주기마다 창 순서를 **읽는다**: 오버레이 창에서 위쪽으로 창 순서를 따라가며 그 위에 있는
  창들의 핸들 값을 모으고(`overlay_win32::OverlayWindow::windows_above`), 그 안에 게임 창이 있으면 게임이 위다.
- 언제 올릴지는 순수 함수가 정한다(`src-tauri/src/stay_on_top.rs`의 `StayOnTop::step`):

  | 상태 | 하는 일 |
  |---|---|
  | 오버레이를 숨겨 뒀다(`Alt+Shift+O`) | 올리지 않는다(창 순서도 읽지 않는다) |
  | 게임 창이 없다(게임 없음·런처만) / 최소화돼 있다 | 올리지 않는다 |
  | 오버레이가 이미 게임보다 위다 | 아무것도 하지 않는다 — 다른 항상 위 창이 오버레이 위에 있어도 게임이 아니면 다투지 않는다 |
  | 게임이 오버레이보다 위다 | 올린다 |
  | 창 순서를 읽지 못했다 | 게임이 **방금 전경이 됐을 때 한 번만** 올린다 |

- 올리는 호출은 `SetWindowPos(오버레이 창, HWND_TOPMOST, …, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_ASYNCWINDOWPOS)` 하나다
  (`OverlayWindow::raise_without_activating`). 자리·크기를 바꾸지 않고 **활성화하지 않는다** — 게임의 키보드 포커스는 그대로다
  (§포커스와 같은 원칙). 숨긴 창을 보이게 하는 표시도 없다.
- **게임 창은 건드리지 않는다.** 창 순서를 바꾸는 호출의 대상은 `OverlayWindow`뿐이고, `OverlayWindow`는 **이 프로세스의 창**으로만
  만들어진다(다른 프로그램의 창 핸들을 넣으면 만들어지지 않는다). 그 호출은 앱 전체에서 그 한 곳에만 있다 —
  `tests/contract.test.ts` 「게임 위에 머물기(Rust)」가 확인한다. 게임 창을 옮기기·크기 바꾸기·활성화·입력 보내기는 여전히 없다.
- 이벤트를 듣는 방식(창 훅)은 쓰지 않는다 — 주기적으로 읽기만 한다. 주기(`stay_on_top::watch_interval`):

  | 상태 | 다시 보는 간격 |
  |---|---|
  | 게임 창을 모른다(게임 없음·런처만) | 1초 — 붙이기가 켜져 있어도(창 목록을 처음부터 훑어야 해서) |
  | 붙이기가 켜져 있고 게임 창을 안다 | 0.05초 |
  | 오버레이가 보이고 게임 창을 안다(떠 있든 최소화돼 있든) | **0.1초** |
  | 오버레이를 숨겨 뒀다 | 1초 |

  게임을 누른 뒤 오버레이가 다시 보이기까지 길어야 한 주기(0.1초) + 올리는 시간이다 — 0.3초 안쪽이다. 그 사이(최대 0.1초)에는
  오버레이가 게임에 가려져 있다. 오버레이를 다시 보이게 하면(`Alt+Shift+O`, 두 번째 실행) 주기를 기다리지 않고 곧바로 본다.
- 이 주기 때문에 오버레이가 보이는 동안에는 게임 창 상태를 0.1초마다 읽는다(찾아 둔 창 하나의 속성만 — 창 목록 전체는 1초에
  한 번). 예전에는 붙이기를 끄면 1초마다였다.

**붙이기의 가장자리 처리**(`game_window.rs`의 `follow_target`·`follow_step` — 순수 함수):

- 게임 창이 **최소화되면** 오버레이는 마지막 자리에 머문다. Windows는 최소화한 창을 화면 밖 좌표(-32000, -32000)에 두는데, 그
  좌표로는 따라가지 않는다(상태가 「최소화」가 아니라고 읽힌 순간에도 좌표가 -30000보다 바깥이면 가지 않는다). 다시 띄우면 붙는다.
- 게임이 **다른 모니터로** 가면 그 모니터의 좌표(왼쪽·위 모니터는 음수)로 따라간다. 배율이 다른 모니터라 오버레이의 너비·여백이
  달라지면 다음 주기에 다시 맞춘다.
- 게임이 **꺼지면** 붙이기는 켜진 채로 기다린다(오버레이는 그 자리). 게임이 다시 뜨면 — 같은 자리여도 — 새로 붙는다.
- 게임 창이 가만히 있는 동안 사용자가 오버레이를 끌어 둔 자리는 되돌리지 않는다(예전과 같다).

**확인한 것.**

- 규칙: Rust 단위 테스트(`stay_on_top.rs` — 숨김·게임 없음·최소화·이미 위·게임이 위·순서를 못 읽을 때, 창 순서를 읽는 조건, 주기가
  0.3초 안쪽 / `game_window.rs` — 최소화, 다른 모니터, 게임이 꺼졌다 다시 뜸 / `overlay_win32.rs` — 올릴 때의 표시, 다른 프로세스의
  창으로는 `OverlayWindow`를 만들 수 없음).
- 실제 창(`tests/live_stay_on_top.rs`, `#[ignore]` — 게임 불필요): 오버레이 역할의 항상 위 창을 띄우고, 그 자리에 게임 역할의 항상 위
  창을 띄워 **활성화**해 덮은 뒤(창 순서와 화면 픽셀로 덮였는지 확인), 앱이 쓰는 호출 그대로 올린다. 올린 뒤 오버레이 역할의 창이
  위에 오고(창 순서·화면 픽셀), **전경 창은 바뀌지 않고**, 두 창의 자리·크기가 그대로다. 게임 역할의 창을 **다른 프로세스**가 가진
  경우도 본다(실제 게임이 그렇다).

  ```bash
  cargo test --manifest-path app/src-tauri/Cargo.toml --test live_stay_on_top -- --ignored --nocapture --test-threads=1
  ```

  돌려 본 결과(2026-11-12, Windows 11 26300): 두 건 모두 통과, 올리기를 부른 뒤 약 11ms에 위로 왔다(세 번씩). **첫 실행에서는 두 건이
  실패했다** — 한 건은 올린 뒤 전경 창이 제3의 창(오버레이 역할의 창이 아니다)으로 바뀌어 있었고, 한 건은 Windows가 게임 역할의 창을
  전경으로 만들어 주지 않았다. 둘 다 테스트를 돌리는 데스크톱의 포커스 상태에 달린 것으로 본다(그 뒤 세 번은 같은 코드로 통과했다 —
  원인을 확정하지는 못했다). 2~3초 동안 화면 왼쪽 위에 초록 창과 자홍색 창이 뜨고, 초록 창이 잠깐 키보드 입력을 받는다.

**확인하지 못한 것 — 실제 게임 위에서는 한 번도 보지 않았다**(§사람이 확인할 것):

- 실제 니케 창이 덮었을 때 오버레이가 다시 올라오는지. 니케는 관리자 권한으로 돈다 — 권한이 낮은 오버레이가 자기 창을 그 위로
  올리는 것이 막히는지는 테스트 창(같은 권한)으로는 알 수 없다.
- 게임이 스스로 주기적으로 맨 위로 올라오는 창이라면 0.1초마다 서로 자리를 바꿔 오버레이가 깜박일 수 있다.
- 전용 전체 화면에서는 이 방법으로도 보이지 않을 수 있다(창 순서와 무관하게 화면을 독점한다).
- 올라올 때 게임 조작(끌기·누르기)이 끊기지 않는지.

## 화면 인식 (요격전)

캡처한 게임 화면에서 **화면 종류**와 **선택된 보스**를 알아낸다(P-019). 오버레이는 이 결과로 그 보스의 추천 편성을
자동으로 보여 준다(P-021 — §자동 추적). 이 절은 인식 자체다: Rust 모듈(`src-tauri/src/recognize.rs`), 명령줄,
한 번 인식하는 앱 명령 `recognize_game_screen`, 프런트의 타입(`ScreenRecognition`)과 `backend.ts`의 `recognizeGameScreen()`.

```bash
cargo run --quiet --manifest-path app/src-tauri/Cargo.toml --bin nikke-capture -- --recognize data/captures/<파일>.png
cargo run --quiet --manifest-path app/src-tauri/Cargo.toml --bin nikke-capture -- --recognize-live    # 게임 창을 찍어 인식만(저장 안 함)
```

결과(JSON 한 줄, 앱 명령도 같은 모양):

```json
{"screen":"anomaly_select","boss":{"id":"kraken","name":"크라켄"},"confidence":1.0,
 "evidence":["아래 띠 주황 100%(화면 맨 아래 가장자리)","보스 선택 화면의 표지: 왼쪽 화살표 주황 47%, 오른쪽 화살표 주황 48% / 아래 탭 빨강 — … / 필수 아님 — 도전하기 단추 주황 86%","→ 이상 개체 보스 선택 화면, 보스 크라켄(테마 색 주황)"],
 "width":1881,"height":1058}
```

| `screen` | 뜻 |
|---|---|
| `anomaly_select` | 이상 개체 요격전 — 보스 선택 화면. `boss`가 있다 |
| `anomaly_squad` | 이상 개체 요격전 — 편성 화면(`도전하기` 뒤). `boss`가 있다 |
| `other` | 이상 개체 화면이 아니다(무슨 화면인지는 가리지 않는다). `boss`는 null |
| `unknown` | 판단하지 않았다: 필수 표지가 일부만 보임, 두 보스의 색이 섞임, 지원하지 않는 프레임. `boss`는 null, `confidence`는 0 |

`boss`의 `id`·`name`은 보스 묶음(`data/intercept/anomaly.json`)과 같다(단위 테스트가 대조한다). `evidence`는 무엇을 보고
그렇게 판단했는지를 적은 한국어 문장들이다. `confidence`는 이상 개체 화면이면 0.5(모든 표지가 기준에 겨우 닿음)~1(캡처에서 잰
값만큼 뚜렷함), `other`는 아래 띠 자리에 테마 색이 적을수록 1에 가깝다. **기준에 못 미치면 추측하지 않는다** — 보스를 다른
보스로 잘못 말하느니 `unknown`으로 둔다.

**요격 횟수를 다 쓴 날**(P-023): 전투로 들어가는 단추(`도전하기`·`전투 진입`)가 제 색이 아니어도 나머지 표지로 인식한다.
그때는 `evidence`에 한 줄이 더 붙고(`전투 진입 단추가 빨강이 아니다(빨강 0%, 평소 55% 이상) — 필수 표지가 아니어서 나머지
표지(…)로 판단했다. …`) `confidence`는 0.8을 넘지 않는다 — §방법의 「필수가 아닌 단추」.

### 방법

글자를 읽지 않는다(OCR·ML 없음, 새 의존성 없음). **정해 둔 자리 열두 곳의 색**만 본다. 자리마다 격자로 점을 찍어(모두 2,000점,
프레임 크기와 무관 — 1881×1058 프레임의 0.1%) 그 점의 색이 무엇인지 센다. 프레임 전체는 한 번도 훑지 않는다.

이상 개체 화면은 보스마다 테마 색이 다르고, 그 색이 화면 여러 곳에 같이 쓰인다:

| 보스 | 테마 색 | 캡처에서 잰 색상 | 그 보스로 치는 색상 범위 |
|---|---|---|---|
| 인디빌리아 | 초록 | 139~147° | 129~157° |

판정(`decide`):

1. **선택 화면**: 좌우 화살표가 둘 다 같은 보스 색으로 기준 이상이고, 아래 탭은 이상 개체 요격전 쪽만 빨강이다.
2. **편성 화면**: 이름 칸 좌우 막대와 정보 칸 좌우 날개가 모두 같은 보스 색으로 기준 이상이고, `모의전`이 파랑이다.
3. 둘 중 하나가 갖춰졌고 **아래 띠도 같은 보스 색**이면 그 화면·그 보스다.
4. 아래 띠 자리에 테마 색이 없고(8% 미만) 어느 화면의 표지도 갖춰지지 않았으면 `other`.
5. 그 밖은 모두 `unknown`: 필수 표지가 하나라도 빠짐, 한 자리에 두 보스의 색(둘째 색이 첫째의 1/4 이상), 표지와 아래 띠의 보스가 다름,
   두 화면의 표지가 함께 보임, 표지는 있는데 아래 띠가 없음, 아래 띠만 있음, `도전하기` 단추가 다른 보스의 색.

**필수가 아닌 단추**(P-023). 처음에는 `도전하기`·`전투 진입`도 필수 표지였다. 2026-11-12 사용자가 그날의 요격 횟수를 다 쓴 뒤
인디빌리아 편성 화면에서 `--recognize-live`를 돌리자 `unknown`이 나왔다 — 나머지 표지는 평소 그대로였고(아래 띠 초록 100%,
막대 69%·77%, 날개 64%·47%, `모의전` 파랑 95%) **`전투 진입`만 빨강 0%**였다. 한 단추의 색에 전부를 걸지 않도록 바꿨다:

| 단추 | 읽힌 것 | 판정 |
|---|---|---|
| `전투 진입`(편성) | 빨강 55% 이상 | 평소 — 신뢰도에 넣는다 |
| | 그 밖(무슨 색이든) | 나머지 표지로 인식. 근거에 `전투 진입 단추가 빨강이 아니다(빨강 N%, 평소 55% 이상) — …`, 신뢰도 0.8 이하 |
| `도전하기`(선택) | 좌우 화살표와 같은 보스 색 55% 이상 | 평소 — 신뢰도에 넣는다 |
| | 테마 색 없음(8% 미만), 또는 같은 보스 색이 55% 미만 | 나머지 표지로 인식. 근거에 `도전하기 단추가 테마 색이 아니다 …`, 신뢰도 0.8 이하 |
| | **다른 보스의** 테마 색(조금이라도 — 8% 이상), 두 보스의 색이 섞임 | 선택 화면이라고 하지 않는다 → `unknown`(근거에 `도전하기 단추는 주황(크라켄) 색인데 좌우 화살표는 …`) |

필수 표지는 그대로 엄격하다 — 단추가 제 색이 아닌 화면에서 필수 표지가 하나라도 빠지거나 다른 보스를 가리키면 `unknown`이다.
단추를 빼도 일반·특수 개체 편성 화면(같은 `모의전`·`전투 진입`이 있다)과 헷갈리지 않는다: 그 화면에는 아래 띠·막대·날개가 없고
`모의전` 자리의 파랑도 64% 이하다. 신뢰도 상한 0.8은 어림값이고 화면에 보이는 숫자일 뿐이다(판정에 쓰지 않는다).

보스 그림(육각형 안)은 보지 않는다 — 그림에는 다른 보스의 테마 색이 섞여 있고(울트라의 붉은 입, 크라켄의 금색), 선택된 육각형의
테두리는 자리가 캡처마다 달랐고(인디빌리아 두 장만 위쪽이 12픽셀쯤 낮다) 울트라에서는 색도 다르다(자홍 — `docs/intercept.md` §인식 근거).

프레임은 **16:9(±3%)만** 판단한다. 자리의 비율을 16:9 화면에서만 쟀기 때문에 4:3·21:9 같은 프레임은 틀린 답 대신
`unknown`(근거에 "화면 비율 …는 지원하지 않는다")이다. 640×360보다 작은 프레임, 픽셀 수가 크기와 맞지 않는 프레임도 `unknown`이다.

### 기준값을 어떻게 정했는지

2026-11-12에 사용자가 찍어 준 캡처 16장(`data/captures/`, 라벨 `labels.json` — 이상 개체 선택 6장·편성 5장, 로비·요격전 탭·
일반 개체 편성 2장·특수 개체 편성)을 이 작업을 한 세션이 이미지를 직접 보고 자리를 골랐다. 그다음 저장소 밖의 임시 스크립트로

- 후보 자리마다 채도 높은 픽셀의 색상 분포를 재서 보스별 색상 범위를 정하고(위 표의 "캡처에서 잰 색상"에 10° 안팎의 여유),
- 16장을 원본·0.34배·0.6배·0.8배·1.25배(가까운 픽셀·쌍선형·평균)·밝기 ±10%·잡음 ±8/±16으로 바꿔 가며 자리별 몫의 최소·최대를
  재고, "있는 화면의 최솟값"과 "없는 화면의 최댓값" 사이에 기준을 뒀다(위 표의 마지막 열).

코드에 들어간 것은 **수치뿐**이다(자리 비율, 색상 범위, 몫의 기준). 게임 이미지 조각(픽셀 템플릿)은 저장소에 없고, 캡처는
gitignore다. 단위 테스트는 코드로 그린 합성 화면(색 사각형)으로 한다.

게임 UI가 바뀌면(자리·색) 기준값을 다시 재야 한다: 새 캡처에 라벨을 붙이고 `live_recognize`를 돌리면 어느 자리가 어긋났는지
근거 문장에 나온다.

시간 포함, PNG를 읽는 시간 제외):

|---|---|---|

찍어 보는 점이 2,000개로 고정이라 해상도가 커져도 같다. 게임 화면을 찍는 쪽이 훨씬 오래 걸린다(한 번에 약 20ms,

### 확인한 것과 한계

- 라벨 캡처 16장 전부 정답(`live_recognize`): 원본, 0.6·0.8·1.25배(가까운 픽셀·쌍선형), 1280×720·1920×1080으로 바꾼 것,
  밝기 ±10%·잡음 ±8. 4:3·21:9로 자르거나 늘리면 `unknown`. P-023 뒤에도 16장의 답은 그대로다.
- **요격 횟수를 다 쓴 화면의 캡처는 없다**(P-023). 아는 것은 사용자가 돌린 `--recognize-live`의 근거 한 건(인디빌리아 편성 화면,
  `전투 진입` 빨강 0%)뿐이고 그 화면을 눈으로 보지 못했다 — "횟수를 다 써서"라는 원인도 추정이다. 확인은 두 가지로만 했다:
  합성 이미지(단추를 회색·어두운 색으로 그린 선택·편성 화면 — 보스 5종 × 크기 7가지)와, **실제 캡처의 단추 자리만 회색으로
  덧칠한 것**(`live_recognize`의 `captures_with_the_battle_button_greyed_out_get_the_same_answer` — 16장 × 회색 4가지, 줄이기·
  밝기·잡음 포함). 보스 선택 화면의 `도전하기`가 그 상태에서 어떤 색인지는 **모른다**: 회색이거나 그대로면 인식하고,
  다른 보스의 테마 색으로 읽히는 색(예: 모든 보스에서 붉은 단추)이면 그 보스가 아닌 화면은 `unknown`이 된다. 그 밖에
  다른 표지(아래 띠·화살표·막대)까지 달라지는 상태라면 여전히 `unknown`이다. 소진 상태의 화면을 `nikke-capture --name`으로
  찍어 `labels.json`에 넣으면 `live_recognize`가 그대로 확인한다.
- 실제 게임에서 `--recognize-live`를 두 번 돌렸다(2026-11-12, 창 모드 1881×1058): 그때 게임은 니케 목록 화면이었고 `other`로
  나왔다(따로 저장해 눈으로 확인한 뒤 지웠다). **이상 개체 화면을 띄워 놓고 라이브로 돌려 본 적은 없다** — 사람이 확인한다.
- **한 계정·하루·한 창 크기(1881×1058)의 캡처로 맞춘 값이다.** 다른 창 크기·전체 화면은 다시 샘플링한 이미지로만 봤다 —
  게임이 창 크기에 따라 UI를 똑같은 비율로 그리는지는 확인하지 않았다. 16:9가 아닌 화면에서 게임이 어떻게 그리는지도 모른다
  (그래서 판단하지 않는다).
- **보스는 테마 색으로만 가린다.** 보스가 늘거나 테마 색이 바뀌면 틀릴 수 있다. 다섯 보스의 색이 서로 멀어서(가장 가까운
  빨강·주황도 캡처에서 잰 값으로 23° 떨어져 있다) 지금은 여유가 있다.
- **아래 띠에 기댄다.** 띠가 가려지거나 없는 변형 화면이면 `unknown`이다. 반대로 이상 개체가 아닌 화면의 맨 아래에 테마 색 띠가
  있으면 `other`가 아니라 `unknown`이 된다(틀린 보스를 말하지는 않는다).
- 보스를 넘기는 도중·화면 전환 중·팝업(장비 보유 현황 등)이 덮인 화면은 캡처가 없어 확인하지 못했다. 색이 섞이거나 어두워지면
  `unknown`·`other`가 되도록 만들었고 합성 이미지로는 확인했다.
- `other`는 "이상 개체 화면이 아니다"까지다. 요격전 탭·일반 개체 편성·로비를 서로 가리지 않는다.
- HDR·색 필터가 켜진 화면에서 색이 어떻게 찍히는지는 확인하지 않았다.

## 자동 추적 (요격전)

게임에서 이상 개체 요격전 화면(보스 선택·편성)을 보고 있으면 오버레이가 그 보스의 추천 편성을 스스로 보여 준다(P-021).
§화면 인식(P-019)과 요격전 화면(P-017)을 이은 것이다. **게임은 읽기만 한다** — 캡처(§캡처 방식)로 화면을 찍어 색을 셀 뿐
입력·창 조작·메모리 접근이 없다. **찍은 이미지는 저장하지도 화면(웹뷰)에 넘기지도 않는다** — 인식이 끝나면 버리고,
화면에 가는 것은 인식 결과(화면 종류·보스·근거 문장)뿐이다.

### 쓰는 법

요격전 탭의 실행 칸 아래에 `자동 추적` 칸이 있다.

| 무엇 | 동작 |
|---|---|
| `자동 추적` 스위치 | 켜면 주기마다 게임 화면을 읽는다. **기본은 꺼짐**이고, 켜 둔 것은 기억해 다음 실행 때 앱이 뜨면서 다시 켠다(요격전 탭을 열지 않아도) |
| 상태 한 줄 | `크라켄 · 보스 선택 화면` / `이상 개체 화면 아님` / `인식 못 함` / `게임 없음` / `게임 창 최소화` / `읽기 실패 (연속 3회)` / `꺼짐`. 그 아래에 이유 한 줄(읽지 못한 까닭, `마지막 보스 크라켄 유지`) |
| `읽음 14:03:22` | 마지막으로 게임 화면을 읽은 시각(현지 시각) |
| `인식 근거·설정`(펼친다) | 인식의 근거 문장들(§화면 인식의 `evidence` — 틀린 인식을 알아챌 수 있게), `캡처 1회 21ms · 프레임 1881×1058 · 신뢰도 0.97`, 주기(초), `인식하면 요격전 탭으로` |
| 주기(초) | 기본 2초. 0.5~60초로 맞춘다(범위는 Rust가 다시 확인한다). 기억한다 |
| `인식하면 요격전 탭으로` | 기본 켜짐. 끄면 탭은 그대로 두고 보스만 고른다. 기억한다. **계산이 도는 동안에는 켜져 있어도 탭을 옮기지 않는다**(아래 §계산 중에는 탭을 옮기지 않는다) |

인식한 보스의 추천을 보일 수 없으면 결과 자리 위에 주황 테두리 안내가 뜬다 — **계산은 스스로 시작하지 않는다**(실행 단추는
사용자가 누른다):

- 추천 결과가 아직 없다: `게임에서 보고 있는 보스: 크라켄 — 추천 결과가 아직 없다. 요격전 추천을 먼저 실행하라`.
- 지금 결과에 그 보스가 없다(다른 보스 묶음으로 계산한 결과): `… 지금 결과에는 이 보스가 없다. 이 보스가 든 보스 묶음으로 …`.
  이때 고른 보스는 바꾸지 않는다.

인식한 보스는 결과의 보스와 `id`로 맞추고(인식의 `id`는 `data/intercept/anomaly.json`과 같다), 없으면 이름으로 맞춘다.

### 언제 읽는가 (Rust — `src-tauri/src/screen_track.rs`)

스위치가 **켜져 있고**, 오버레이가 **보이고**, 게임 창이 **떠 있을 때만**(찾았고 최소화되지 않았다) 주기마다 한 번 읽는다.
그 밖에는 캡처하지 않는다:

| 상태(`state`) | 뜻 | 캡처 |
|---|---|---|
| `off` | 스위치가 꺼져 있다 — 추적 스레드는 깨울 때까지 잔다(창 열거도 하지 않는다) | 안 함 |
| `starting` | 켰고 아직 한 번도 읽지 않았다 | — |
| `read` | 읽어서 인식했다(`recognition` — `unknown`·`other`도 읽은 것이다) | 함 |
| `overlay_hidden` | 오버레이를 숨겼다(`Alt+Shift+O`) — 게임 창을 찾지도 않는다 | 안 함 |
| `no_game` | 게임이 없다(런처만 떠 있는 것 포함) | 안 함 |
| `minimized` | 게임 창이 최소화돼 있다(복원하지 않는다) | 안 함 |
| `failed` | 읽으려 했지만 실패했다(창 정보·캡처 오류, 검은 화면 등). `failures`가 연속 횟수 | 시도함 |

- **실패는 상태다.** 오류를 쌓지 않고 상태 하나와 연속 횟수만 남기며 다음 주기에 다시 본다 — 게임이 다시 뜨면 스스로 이어진다.
  읽는 도중의 예기치 못한 오류(패닉)도 `failed`로 바꾸고 계속한다. 추적 스레드는 끝나지 않는다.
- **결과가 바뀔 때만 이벤트(`screen-track`)를 보낸다.** 가르는 값은 켜짐·주기·상태·이유·화면 종류·보스다. 읽은 시각·걸린 시간·
  근거 문장의 수치만 달라진 것은 보내지 않는다 — 추적 칸이 보이는 동안 주기마다 상태 명령(`screen_track_status` — 캡처가
  아니라 마지막 상태를 읽을 뿐이다)으로 물어 `읽음` 시각과 근거를 최신으로 둔다.
- 저장용 캡처(`화면 저장`·`Alt+Shift+S`)와 겹치면 그 주기를 건너뛴다(한 번에 하나만 찍는다). 반대로 추적이 찍는 순간에
  `화면 저장`을 누르면 `이미 캡처하고 있다`가 나올 수 있다 — 다시 누르면 된다.
- 오버레이를 다시 보이거나 설정을 바꾸면 주기를 기다리지 않고 바로 한 번 읽는다.
- 추적 스레드(`screen-tracker`)는 게임 창 추적 스레드(`game-tracker` — 붙이기)와 따로다. 캡처가 붙이기를 늦추지 않는다.

상태의 모양(명령 `set_screen_tracking(enabled, interval_ms)`·`screen_track_status()`의 반환값이자 이벤트의 내용):

```json
{"enabled":true,"interval_ms":2000,"state":"read","message":"이상 개체 요격전 보스 선택 화면 — 크라켄",
 "recognition":{"screen":"anomaly_select","boss":{"id":"kraken","name":"크라켄"},"confidence":0.97,"evidence":["…"],"width":1881,"height":1058},
 "read_at":"2026-11-12T05:03:22.000Z","capture_ms":21,"failures":0}
```

`recognition`은 `state`가 `read`일 때만 있다. `read_at`은 마지막으로 읽기에 성공한 시각(UTC)이고 읽지 못하는 동안에도 남는다.

### 언제 보스를 바꾸는가 (화면 — `src/lib/screenTrack.ts`의 `followStep`)

순수 함수 하나가 정한다. 탭을 옮기는 것(`App.vue`)과 보스를 고르는 것(`InterceptView.vue`)은 이 함수가 "따라가라"고 할 때만 한다.

| 들어온 것 | 하는 일 |
|---|---|
| 이상 개체 화면 + 보스, **마지막으로 따라간 것(화면 종류 + 보스)과 다름** | 따라간다: (자동 이동이 켜져 있으면) 요격전 탭으로 옮기고 그 보스를 고른다 |
| 같은 것이 이어짐 | 아무것도 하지 않는다 — 그 사이에 손으로 고른 보스·옮긴 탭은 그대로다 |
| `unknown`, 읽지 못한 상태(게임 없음·최소화·오버레이 숨김·읽기 실패·시작 전) | 아무것도 바꾸지 않고, 마지막으로 따라간 것도 잊지 않는다 — 잠깐 모르게 됐다가 같은 화면으로 돌아와도 손으로 고른 보스를 되돌리지 않는다 |
| `other`(이상 개체 화면이 아님) | 고른 보스는 바꾸지 않는다. 다만 이상 개체 화면을 떠난 것이므로 마지막으로 따라간 것을 잊는다 — 다시 들어오면 같은 보스여도 새로 따라간다 |
| 스위치가 꺼져 있음 | 들어온 것을 무시한다. 다시 켜면 지금 화면부터 새로 따라간다 |

같은 보스의 선택 화면 ↔ 편성 화면은 "다른 것"이다(들어갈 때마다 그 보스를 다시 고른다). `other`와 `unknown`을 다르게 다룬
것은 판단이다: `other`는 "이상 개체 화면이 아니다"라고 확인한 것이고 `unknown`은 판단하지 않은 것이다. 실제 게임에서 보스를
넘기는 도중·팝업·전투 화면이 어느 쪽으로 나오는지는 확인하지 못했다(§화면 인식 §확인한 것과 한계) — 손으로 고른 보스가 자꾸
되돌아가면 이 구분을 다시 봐야 한다.

### 계산 중에는 탭을 옮기지 않는다 (`src/lib/screenTrack.ts`의 `tabMoveStep`)

예전에는 다른 탭에서 계산을 돌려 놓고 보고 있을 때 보스가 인식되면 탭이 요격전으로 넘어갔다 — 계산은 계속 돌지만 보고 있던 화면이
갑자기 바뀌었다(P-024에서 고쳤다). 보스를 따라갈 때 탭을 옮길지는 순수 함수 `tabMoveStep`이 정한다. `App.vue`는 묻는 것(계산이
도는가, 요격전 탭인가)에 답하고 시키는 대로 옮길 뿐이다.

| 상황 | 하는 일 |
|---|---|
| 보스를 따라갔고, 계산이 돌지 않는다 | 요격전 탭으로 옮긴다(예전과 같다) |
| 보스를 따라갔는데 **어느 탭에서든 계산이 돌고 있다** | 탭은 그대로 둔다. 보스는 요격전 화면의 선택에 반영하고(다음에 열면 그 보스다), 탭 줄 아래에 `게임에서 보고 있는 보스: 크라켄 — 계산이 끝나면 요격전 탭으로 옮긴다`를 보인다 |
| 그 계산이 끝났다(결과·오류·중단 어느 쪽이든) | 그때 **한 번** 옮긴다 |
| 계산 중에 사용자가 요격전 탭을 직접 열었다 | 미뤄 둔 이동을 버린다 — 다른 탭으로 돌아가 있어도 계산이 끝났을 때 옮기지 않는다 |
| 계산 중에 게임이 이상 개체 화면을 떠났다(`other`), 스위치·자동 이동을 껐다 | 미뤄 둔 이동을 버린다 |
| 계산 중에 잠깐 `unknown`·읽기 실패가 됐다 | 미뤄 둔 이동을 그대로 둔다 |
| `인식하면 요격전 탭으로`가 꺼져 있다, 이미 요격전 탭이다 | 옮기지도 미루지도 않는다 |

「계산이 돈다」는 엔진 계산(추천·비교, 요격전, 성장)이 도는 동안이다(`lib/engineRun.ts`의 계산 주인 — 탭의 점과 같은 값). 계정
수집(계정 탭)은 여기에 들지 않는다. 확인: `tests/ScreenTrack.test.ts`(규칙의 경우들 + 엔진을 붙들어 둔 채 이벤트를 보내는 화면 흐름
일곱 건). 실제 창에서는 보지 않았다.

### 걸리는 시간

`tests/live_track.rs`로 쟀다(2026-11-12, 이 PC, Windows 11 26300). 대상은 **테스트가 띄운 자기 창**(화면 영역 1904×1061 — 게임의
창 모드 1881×1058과 비슷한 크기, 네 구역을 다른 색으로 칠함)이다. 캡처 한 번 = `capture_window`(세션을 만들고, 프레임 하나를
받아 화면 영역을 CPU 메모리로 읽고, 닫는다). 인식은 그 뒤에 50µs(릴리스)쯤이다.

| 방식 | 릴리스: 첫 회 | 릴리스: 그 뒤 중앙값(최소~최대) | 디버그: 그 뒤 중앙값 | 2초쯤 멈춘 캡처 |
|---|---|---|---|---|
| 캡처마다 전부 새로 만든다(P-011 때의 방식) | 264~282ms | 202~203ms(195~219) | 245ms | 300회 중 0 |
| Direct3D 장치만 다시 쓴다 | 251~260ms | 65~68ms(59~92) | 105ms | **940회 중 9회**(2.04~2.08초) |
| 장치와 캡처 대상을 다시 쓴다(**지금**) | 253~261ms | **21.5ms**(16~30) | 65ms(61~66) | 800회 중 0 |

- **캡처마다 Direct3D 장치와 세션을 새로 만들면 느리다**: 한 번 약 200ms 가운데 장치 만들기가 약 142ms, 캡처 대상·프레임 풀·
  세션 만들기가 약 36ms, 첫 프레임을 기다려 읽기가 약 13ms, 닫기가 약 12ms였다(릴리스, 구간별로 따로 잰 값).
- 그래서 장치를 한 번만 만들게 했더니 65ms로 줄었지만 **100번에 한 번쯤 캡처가 2초 동안 멈췄다.** 멈춘 곳은 캡처 대상을
  만드는 호출(`CreateForWindow` 쪽)이었고, 캡처 사이를 0.15초로 두든 0.5초로 두든 나왔다. 전부 새로 만들 때는 300회 동안
  한 번도 없었다. **원인은 모른다**(추정도 확인하지 못했다).
- 캡처 대상도 창이 같은 동안 다시 쓰게 하자 그 호출 자체가 없어져 멈춤이 사라졌고(0.15초 간격 400회 + 0.5초 간격 400회),
  한 번이 약 20ms가 됐다. 기본 주기 2초의 1%쯤이다. 프레임 풀과 세션은 여전히 캡처마다 만들고 닫는다.
- 다시 쓰는 것 때문에 달라질 수 있는 경우를 같은 테스트 파일이 본다: 창 크기를 바꿔도 바뀐 화면 영역이 그대로 찍힌다
  (세 번 바꿔 가며), 찍던 창이 없어지고 다른 창이 떠도 새 창이 찍힌다. P-011의 `live_capture` 네 건도 그대로 통과한다.
  **`live_game`(실제 게임 창 5건)은 이 작업에서 돌리지 못했다** — 작업하는 내내 게임 창이 최소화돼 있었다.
- **게임 창으로는 재지 못했다**(같은 이유). 게임은 Direct3D로 계속 그리는 창이라 값이 다를 수 있다 — 게임 창을 띄우고
  `capture_cycle_time_on_the_game_window`를 돌리면 같은 표가 나온다. 추적 칸의 `캡처 1회 …ms`도 실제 값을 보여 준다.
- **게임이 느려지는지는 재지 않았다.** 캡처는 합성기가 창 화면을 텍스처로 복사해 주는 것이고 2초에 한 번이지만, 게임의
  프레임 시간에 주는 영향은 사람이 봐야 한다(§사람이 확인할 것).

```bash
cargo test --release --manifest-path app/src-tauri/Cargo.toml --test live_track -- --ignored --nocapture --test-threads=1
```

환경 변수 `NIKKE_TRACK_ROUNDS`(횟수, 기본 12)와 `NIKKE_TRACK_GAP_MS`(캡처 사이 간격, 기본 500)로 길게 돌릴 수 있다.
캡처 한 번이 주기의 하한(500ms)보다 길면 테스트가 실패한다.

### 확인한 것과 한계

- 규칙: Rust 단위 테스트(`screen_track.rs` — 읽는 조건 스무 조합, 같은 결과는 한 번만 알림, 실패 열 번이 상태 하나, 게임이
  돌아오면 이어짐, 끄는 순간 늦게 온 읽기 버림)와 화면 테스트(`tests/ScreenTrack.test.ts` — `followStep`의 경우들, 가짜 backend로
  이벤트를 보내 탭·보스가 바뀌는지, `unknown`·`other`·읽기 실패에서 안 바뀌는지, 손으로 고른 보스·탭이 남는지, 스위치를 끄면
  무시하는지, 결과가 없을 때 안내만 뜨고 엔진을 부르지 않는지).
- **실제 창에서는 스위치를 켜 보지 못했다.** 추적 스레드와 새 명령 둘은 컴파일·계약 테스트(읽는 순서, 저장·전달 없음,
  권한 목록)까지다. 이 작업을 한 세션에서는 웹뷰를 밖에서 조작할 길이 없었다(WebView2 디버깅 포트가 열리지 않았다).
- **이상 개체 화면을 띄운 채로는 한 번도 돌려 보지 못했다** — 인식 자체가 그렇다(§화면 인식). 실제로 2~3초 안에 따라오는지,
  보스를 넘기는 도중에 다른 보스로 튀지 않는지는 사람이 본다.
- 주기를 0.5초보다 짧게 할 수 없다. 캡처가 실패하며 오래 걸리는 경우(프레임이 오지 않으면 최대 2.5초)에는 그만큼 다음 읽기가 늦다.
- 오버레이를 숨기면 추적이 쉰다 — 숨긴 채로는 보스를 따라가지 않고, 다시 보이는 순간 한 번 읽는다.
- 기억해 둔 요격전 결과가 지금 계정·보스 값과 다른지는 여전히 알려 주지 않는다(§요격전).

## 계정 받기

터미널에서 손으로 하던 세 단계(쿠키를 파일에 저장 → `python vendor/nikke-calc/scraper/profile_fetch.py` →
`node src/cli.mjs import-profile …`)를 **계정** 탭에서 한다(P-022). 화면에 1·2·3 단계가 차례로 있다.

| 단계 | 하는 일 | 누가 |
|---|---|---|
| 1 쿠키 받기 | 방법 셋 가운데 하나: **크롬 확장**의 「오버레이로 보내기」(권장 — §크롬 확장으로 계정 받기), 붙여넣기 칸에 넣고 「쿠키 저장」, 앱 안의 로그인 창에서 「쿠키 가져오기」 → 엔진의 `scraper/.session_cookie`에 한 줄로 저장 | Rust(`cookie.rs`·`account_sync.rs`·`extension_link.rs`·`login_window.rs`) |
| 2 계정 새로 받기 | 엔진의 `scraper/profile_fetch.py --name <이름>` 실행. 스크립트가 낸 줄을 오는 대로 보이고, 끝나면 모든 줄과 경고(`[!]`)를 보인다 | Rust(`account_sync.rs`) — 엔진 스크립트는 고치지 않고 그대로 쓴다 |
| 3 변환·저장 | 받은 프로필 → 계정 상태(루트 `src/core/import-profile.mjs`의 `importProfile`) → `data/accounts/<이름>.json`. 요약(가져온 니케 수·건너뛴 항목·미확인 칸이 있는 니케·동기화 레벨)을 보이고, 추천·비교, 요격전, 성장 화면의 계정 칸에 그 경로를 넣는다 | 변환은 화면 쪽(`src/lib/accountSync.ts` → 루트 모듈), 파일 읽기·쓰기는 Rust |

「계정 새로 받기」 한 번에 2 → 3이 이어진다(크롬 확장으로 받으면 1 → 2 → 3이 확장의 단추 한 번에 이어진다).
이름(기본 `me`)이 엔진의 프로필 이름이자 계정 파일 이름이다. 같은 이름의 계정
파일이 있으면 덮어쓰기 전에 `<이름>.json.bak`으로 한 벌 남긴다(손으로 고친 내용을 되찾을 수 있게 — 사본은 바로 앞의 한 벌뿐이다).
계정 칸에는 경로만 넣는다 — 계산을 스스로 시작하지 않는다.

### 쿠키 받는 법

blablalink의 계정 데이터 API는 로그인 세션 쿠키를 요구한다. 받는 방법은 셋이고 서로 기대지 않는다. 어느 쪽으로 받든 저장된 뒤는
같은 「계정 새로 받기」다. 화면에는 이 순서로 있다:

1. **방법 1 · 크롬 확장(권장)** — 이미 blablalink에 로그인된 브라우저에서 확장의 단추 한 번. 자동 로그인(SSO)으로 써서 비밀번호를
   모르는 계정도 된다. 따로 적었다: §크롬 확장으로 계정 받기.
2. **방법 2 · 쿠키 붙여넣기** — 브라우저의 개발자 도구에서 Cookie 헤더를 복사해 붙여넣는다(아래 「나」).
3. **방법 3 · 앱 안의 로그인 창** — 비밀번호로 로그인하는 사용자용(아래 「가」). 앱 안의 창에서 다시 로그인해야 하므로, 자동
   로그인으로 쓰는 계정은 여기서 로그인할 수 없다.

**가. 로그인 창(방법 3)** — 개발자 도구가 필요 없다.

1. 「blablalink 로그인」을 누르면 별도 창이 뜬다(보통 창 — 테두리·제목 표시줄이 있고 작업 표시줄에 보인다).
2. 그 창에서 **직접** 로그인하고 게임 계정을 연동한다. 아이디·비밀번호는 blablalink와 로그인 제공자의 페이지에 넣는다 — 앱은
   입력을 읽지 않고 그 페이지에 스크립트를 넣지도 않는다.
3. 「쿠키 가져오기」를 누른다. Rust가 그 창의 쿠키 저장소에서 `api.blablalink.com` 요청에 실릴 쿠키만 읽어, `game_token`과
   `game_openid`가 있으면 Cookie 헤더 한 줄로 저장하고 창을 닫는다. 없으면 「아직 로그인되지 않았다」고 알리고 창은 그대로 둔다.

로그인 창에서 로그인이 막히는 로그인 방식이 있을 수 있다(예: 구글 계정은 앱 안의 창을 거부할 수 있다 — **확인하지 않았다**).
그때는 크롬 확장이나 붙여넣기를 쓴다.

**나. 붙여넣기(방법 2)**

1. 브라우저(크롬·엣지)에서 blablalink.com에 로그인하고 게임 계정을 연동한다.
2. F12 개발자 도구 → Network(네트워크) 탭 → 페이지를 새로 고친다.
3. `api.blablalink.com`으로 가는 요청을 하나 눌러, Request Headers의 `Cookie` 값 전체를 복사한다.
4. 계정 탭의 붙여넣기 칸에 붙여넣고 「쿠키 저장」을 누른다. Rust가 앞뒤 공백·줄바꿈을 정리해 한 줄로 만들고(맨 앞의 `Cookie:`는
   뗀다), `game_token=`과 `game_openid=`가 없으면 한국어 오류로 거부한다.

쿠키가 만료되면(수집이 `game not login`으로 실패한다) 같은 순서로 다시 받는다. 쿠키 문제로 실패하면 화면에 이 순서가 함께 보인다.

### 보안 규칙

세션 쿠키는 **계정 접근권**이다. 아래는 코드의 규칙이고 테스트가 확인한다(`src-tauri/tests/account_fetch.rs`,
`tests/AccountFlow.test.ts`, `tests/contract.test.ts`).

- **쓰는 곳은 하나다**: 엔진의 `scraper/.session_cookie`(엔진의 수집 스크립트가 거기서 읽는다 — 엔진 저장소가 gitignore로 둔 파일).
  다른 파일·임시 파일·설정·웹뷰 저장소에 쓰지 않는다. 쿠키 값을 꺼내는 함수(`SessionCookie::header`)를 부르는 곳이 그 한 줄뿐이다.
- **화면에 다시 보이지 않는다**: 붙여넣기 칸은 가려진 형식(`type="password"`)이고, 「쿠키 저장」을 누르면 Rust에 넘기기 전에
  칸을 비운다(거부돼도 남기지 않는다). Rust는 쿠키를 돌려주지 않는다 — 돌려주는 것은 저장한 시각과 쿠키 개수, 「쿠키 저장됨/없음」뿐이다.
  로그인 창으로 받을 때는 쿠키가 오버레이 화면을 지나가지도 않는다.
- **로그·오류·이벤트·반환값·결과 문서·localStorage에 넣지 않는다**: 쿠키를 담는 Rust 타입은 `Debug`에서 값을 가리고 직렬화할 수
  없다. 오류 문장에는 쿠키 이름(`game_token` 같은 정해진 이름)만 나온다. 수집 스크립트가 낸 줄은 **쿠키 값을 가린 뒤에** 화면으로
  넘긴다(`(가림)`으로 바뀐다 — 쿠키 파일의 내용 전체, `이름=값` 조각, 6자 이상인 값. 스크립트가 계정 식별자 openid를 출력하는
  줄도 이렇게 가려진다). 받은 프로필의 `_meta.openid`도 화면에 넘기지 않는다. 계정 받기 코드는 표준 출력·표준 오류에 아무것도
  쓰지 않는다. 화면이 기억하는 것(localStorage)은 계정 이름과 계정 파일 경로뿐이다.
- **앱은 쿠키를 네트워크로 보내지 않는다**: 이 앱에는 HTTP 코드가 없다. 쿠키를 보내는 것은 엔진의 수집 스크립트가 blablalink API에
  하는 요청뿐이다(로그인 창 안에서는 브라우저가 자기 쿠키를 그 사이트에 보낸다 — 여느 브라우저와 같다).
- **화면은 실행할 것을 정하지 못한다**: 수집 명령이 실행하는 것은 설정된 엔진 폴더(§엔진 설정 — 환경 변수 → 설정 파일 →
  `vendor/nikke-calc`)의 `scraper/profile_fetch.py`뿐이고, 화면이 넘기는 것은 이름 하나다. 이름은 글자·숫자·밑줄·붙임표·낱말 사이
  공백만 받는다(48자까지) — 점, 경로 구분자, 붙임표로 시작하는 이름(인자로 읽힌다)은 고치지 않고 거부한다. 계정 파일을 쓸 폴더
  (환경 변수 `NIKKE_ACCOUNTS_DIR` → 저장소의 `data/accounts`, gitignore)도 화면이 정하지 못한다.

### 로그인 창

- **이 창은 앱 명령을 부를 수 없다.** capability(`src-tauri/capabilities/overlay.json`)의 창 목록에는 `main`(오버레이)뿐이고
  로그인 창(`login`)은 없다. 원격 주소에 IPC를 여는 설정(`remote`)도 없다. 권한은 주소가 아니라 창 이름에 붙으므로, **로그인 창의
  주소가 blablalink나 로그인 제공자가 아닌 곳으로 바뀌어도(광고·링크·리디렉션으로 어디로 가든) 앱 명령은 여전히 부를 수 없다** —
  그 창에는 권한이 하나도 없다. 앱 명령은 모두 권한 목록(`build.rs`)에 올라 있어, 권한 없는 창에서는 거부된다.
  이것은 설정과 코드를 읽는 계약 테스트로 확인했다. 실제 창에서 원격 페이지가 명령을 불러 거부되는 것을 본 것은 아니다.
- 갈 수 있는 주소는 `https`뿐이다(`http`·`file`·그 밖의 주소로의 이동은 막는다). 로그인 제공자가 여럿이라 도메인은 묶지 않았다.
- 쿠키는 그 창의 저장소에 「`https://api.blablalink.com/api/game/proxy/`로 가는 요청에 실릴 쿠키」만 묻는다(저장소 전체를 읽지
  않는다). 받은 목록에서 도메인이 `api.blablalink.com`이나 그 윗도메인(`.blablalink.com`)인 것만 골라 `이름=값; 이름=값` 한 줄로
  만든다 — 이 부분은 순수 함수다(`cookie.rs`의 `header_from_browser_cookies`).
- 로그인 창의 저장 데이터(쿠키·로컬 저장소)는 오버레이와 다른 폴더에 둔다: `%LOCALAPPDATA%\local.nikke-companion.overlay\login-webview`.
  그래서 로그인해 두면 다음에 창을 열 때 로그인 상태가 남아 있다.
- **「로그인 세션 지우기」**: 그 폴더의 쿠키·저장 데이터를 지운다 — 다른 계정으로 바꾸거나 공용 PC에서 쓴 뒤에 누른다. 창이 열려
  있으면 그 창의 데이터를 지우고 로그인 전 화면으로 되돌리고, 닫혀 있으면 폴더를 지운다(방금 닫았으면 브라우저 프로세스가 파일을
  잠깐 쥐고 있어 2초까지 다시 해 본다). **엔진의 쿠키 파일은 지우지 않는다** — 그것까지 없애려면
  `vendor/nikke-calc/scraper/.session_cookie`를 직접 지운다. 오버레이가 기억해 둔 것(탭·경로·결과)도 건드리지 않는다.

Tauri에서 창의 쿠키를 읽는 API(`WebviewWindow::cookies_for_url`)와 저장 데이터를 지우는 API(`clear_all_browsing_data`)는 쓰는 판
(tauri 2.12.5)의 문서(`cargo doc`으로 만든 것)에서 확인하고 컴파일했다. Windows에서는 화면 응답을 맡은 스레드에서 쿠키를 읽으면
멈춘다고 문서에 적혀 있어 다른 스레드에서 읽는다.

```bash
cargo test --manifest-path app/src-tauri/Cargo.toml --test live_login_window -- --ignored --nocapture
```

`tests/live_login_window.rs`가 로그인 창을 실제로 띄워 본다(`#[ignore]` — 창이 몇 초 떴다 닫힌다. 네트워크가 필요하다). **임시 저장
폴더와 가짜 엔진 폴더**를 써서 앱의 실제 로그인 세션과 엔진의 쿠키 파일은 건드리지 않고, 로그인은 하지 않는다. 돌려 본 결과
(2026-11-12): 보통 창으로 뜨고(테두리 있음·항상 위 아님), blablalink 첫 페이지가 떠서 사이트가 심은 쿠키 하나(`OptanonConsent`)가
저장소에 보였고, 쿠키 읽기가 다른 스레드에서 멈추지 않고 돌아왔고, 「아직 로그인되지 않았다」로 거부돼 쿠키 파일이 생기지 않았고,
세션 지우기가 창이 열려 있을 때·닫혀 있을 때·지울 것이 없을 때 모두 됐다(저장 폴더가 사라졌다).

### 실패의 안내

수집이 실패하면 2단계 아래에 한국어 문장이 보이고, 스크립트가 그때까지 낸 줄도 그대로 보인다. 쿠키 문제일 때는 쿠키를 다시 받는
순서가 함께 보인다.

| 종류(`kind`) | 언제 | 쿠키 안내 |
|---|---|---|
| `cookie_missing` | 쿠키 파일이 없다(스크립트를 띄우기 전에 알린다) | ○ |
| `cookie_invalid` | 저장된 쿠키에 `game_token`이 없다 | ○ |
| `cookie_rejected` · `not_logged_in` | 붙여넣은 쿠키에 필수 쿠키가 없다 · 로그인 창에서 아직 로그인하지 않았다 | ○ |
| `session_expired` | 스크립트가 `로그인 세션 만료 (game not login)`를 냈다. 또는 `캐릭터를 못 받았다. 세션 만료거나 비공개 계정` — 첫 요청이 거절되면 스크립트는 이 둘을 가르지 못한다 | ○ |
| `network` | 스크립트가 파이썬의 네트워크 예외(`URLError`·`timed out` 등)나 HTTP 오류로 끝났다 | — |
| `timeout` | 10분 안에 끝나지 않았다 — 스크립트와 그 자식 프로세스까지 끝낸다 | — |
| `stopped` | 「중단」을 눌렀다 — 오류가 아니다. `중단됨`으로 보이고 계정 파일은 그대로다 | — |
| `engine` · `name` · `script_failed` · `profile` · `account_file` · `login_window` | 엔진 폴더·python 문제, 쓸 수 없는 이름, 그 밖의 스크립트 실패(마지막 경고 줄이 함께 보인다), 프로필을 못 읽음, 계정 파일을 못 씀, 로그인 창 문제 | — |

실패의 구분은 스크립트가 낸 문장에 기댄다(`account_sync.rs`의 `classify` — 엔진을 올릴 때 스크립트의 문장이 바뀌었는지 함께 본다).
중단과 시간 초과는 엔진 계산 중단(§계산 중단)과 같은 방식이다: 프로세스를 Job Object에 넣어 자식까지 끝낸다.

### 한계

- **큐브는 장착 중인 것만 받는다.** blablalink API는 보유 큐브 목록을 주지 않는다 — 장착 중인 큐브에서 관찰된 것이 계정 파일의
  `account.cubes`에 「보유 하한」으로 기록될 뿐이고, 계산은 엔진 기본 스펙 큐브로 한다(엔진의 `profile-sync` 문서와 같다).
- 레벨은 받지 않는다(콘텐츠가 정한다). 동기화 레벨은 `account.synchro_level`로 옮겨져 레벨 상한이 있는 콘텐츠의 계산에 쓰인다.
- 스크립트가 낸 경고는 그대로 옮겨 보일 뿐 해석하지 않는다. 뜻은 엔진의 `vendor/nikke-calc/.agent/skills/profile-sync/SKILL.md`에 있다
  (`동기화 소대 밖 N종`은 미보유 판정이 아니다, `미매핑 오버로드 옵션 타입`은 그 옵션이 빠진 채 계산된다 등).
- 가져온 값을 인게임과 대조하지 않는다. 변환이 옮기지 못한 칸은 미확인으로 남고, 계산할 때 미육성 값으로 채워져 실제보다 낮게
  나올 수 있다(결과의 주의 문구).
- 화면에 넘기는 줄은 2,000줄·줄마다 2,000자까지다(넘으면 알리는 줄 하나를 남긴다).
- 수집 스크립트는 프로필 옆에 원시 응답(`profiles/<이름>.raw.json`)도 쓴다(엔진의 동작). 앱은 그 파일을 읽지 않는다.
- **실제 계정으로는 돌려 보지 않았다** — 실제 쿠키·실제 수집·실제 로그인은 사람이 확인한다(§사람이 확인할 것). 자동 테스트는
  지어낸 쿠키, 가짜 수집 스크립트, 검증용 샘플 프로필로만 한다.

## 크롬 확장으로 계정 받기

이미 blablalink에 로그인돼 있는 **크롬**의 세션을 단추 한 번으로 넘겨받는다(P-025, 사용자 결정 2026-11-12). 자동 로그인(SSO)으로
쓰는 사용자는 비밀번호를 모르므로 앱 안의 로그인 창(§로그인 창)에서는 로그인할 수 없다 — 그래서 이것이 계정 받기의 기본 경로다.
크롬의 쿠키 저장소 파일을 앱이 직접 읽는 방식은 쓰지 않는다.

```
크롬(blablalink에 로그인돼 있다)                       오버레이
 확장 팝업의 「오버레이로 보내기」
   │ chrome.cookies.getAll — api.blablalink.com 요청에 실릴 쿠키
   │ → Cookie 헤더 한 줄 (game_token·game_openid가 없으면 보내지 않는다)
   └─ POST http://127.0.0.1:47615/nikke-companion/v1/session ──▶ 수신부(extension_link.rs)
        {"code": "<연결 코드>", "cookie": "<헤더 한 줄>"}           │ 출처·호스트·형식·크기 → 연결 코드 → 붙여넣기와 같은 정리·검사
   ◀──────────── {"ok": true, "result": "received"} ──────────────┤ → 엔진의 scraper/.session_cookie
                                                                  └ 화면에 「받았다」 → 계정 화면이 수집 → 변환 → 저장을 잇는다
```

확장 쪽 설명(권한·파일·테스트)은 저장소의 `extension/README.md`.

### 설치 (한 번)

1. 크롬에서 `chrome://extensions`를 연다(엣지는 `edge://extensions`).
2. 오른쪽 위의 **개발자 모드**를 켠다.
3. **압축해제된 확장 프로그램을 로드합니다**를 눌러 이 저장소의 `extension` 폴더를 고른다.

같은 순서가 계정 화면의 「방법 1 · 크롬 확장」에 적혀 있다(꺼져 있을 때는 펼쳐져 있다). **확장의 파일을 고친 뒤에는**
`chrome://extensions`에서 그 확장을 새로 고쳐(↻) 다시 로드해야 한다 — 저장소를 `git pull`로 받은 뒤에도 그렇다.

### 연결 (한 번)

1. 오버레이의 **계정** 탭 → 방법 1에서 **크롬 확장 연결**을 켠다. `켜짐 · 127.0.0.1:47615에서 듣는 중`과 **연결 코드**
   (`ABCD-EFGH` 꼴 여덟 글자)가 보인다.
2. 브라우저 도구 모음의 확장 아이콘을 눌러 팝업의 「연결 코드」 칸에 그 코드를 넣는다. 확장이 기억한다.

- **기본은 꺼짐**이다. 켜 둔 것은 Rust가 기억한다(`%APPDATA%\local.nikke-companion.overlay\extension-link.json` — 켜짐과 코드뿐,
  쿠키는 없다). 켜 둔 채 앱을 끄면 다음에 켤 때 계정 탭을 열지 않아도 곧바로 듣는다. 끄거나 앱이 끝나면 듣는 소켓이 닫힌다.
- **연결 코드**는 오버레이가 운영체제의 난수로 만든다(32글자 × 8자리 — 헷갈리는 I·O·0·1은 쓰지 않는다). 쿠키가 아니라서 화면에
  그대로 보인다. 「코드 다시 만들기」를 누르면 옛 코드는 그 순간부터 받지 않는다(확장에 새 코드를 넣어야 한다).
- 코드가 틀린 요청은 거부하고, **연속 다섯 번 틀리면 1분 동안 모든 요청을 막는다**(맞는 코드도 받지 않는다). 막힌 동안의 요청은
  막힘을 늘리지 않는다. 계정 화면의 「마지막 요청」 줄에 `연결 코드가 틀린 요청이 왔다(연속 N회)`·`잠시 막았다(N초 남음)`가 보인다.

### 쓰기

같은 브라우저에서 blablalink에 로그인돼 있는 채로 확장의 **오버레이로 보내기**를 누른다. 그러면:

1. 수신부가 쿠키를 받아 엔진의 쿠키 파일에 쓰고 확장에 「받았다」고 답한다(팝업: `오버레이가 받았다`).
2. 오버레이가 계정 탭을 열고(계산 중이면 미룬다 — 아래), 계정 화면이 **「계정 새로 받기」를 저절로 이어서** 돌린다 — 수집 → 변환 →
   저장 → 추천·비교, 요격전, 성장 화면의 계정 칸. 진행(받는 중… N초, 스크립트의 줄)과 결과(요약·저장한 파일)는 손으로 눌렀을
   때와 같은 자리에 보인다. 이름 칸에 적어 둔 이름으로 받는다.

확장 팝업에 보이는 안내는 넷이 구분된다: `오버레이가 받았다` / `오버레이가 꺼져 있다`(연결이 거절된다 — 오버레이가 꺼져 있거나
「크롬 확장 연결」이 꺼져 있다) / `연결 코드가 틀리다` / `blablalink에 로그인돼 있지 않다`(이때는 **아무것도 보내지 않는다**).
그 밖에 `잠시 막았다`·`계정을 받는 중이다`·`저장하지 못했다`·`오버레이가 아닌 답이 왔다`가 있다(`extension/README.md`의 표).

- **수집이 도는 동안에는 쿠키를 바꾸지 않는다**: 그동안 온 요청은 `busy`로 거부한다(팝업: `오버레이가 지금 계정을 받는 중이다`).
- 차례는 한 번만 가져간다(Rust의 `take_pending` — 받은 것 하나에 수집 한 번). 「받았다」는 Rust가 들고 있으므로, 앱이 막 켜져
  화면이 뜨기 전에 받은 것도 화면이 뜨면 잇는다(이벤트를 놓쳐도 된다). 계정 화면이 다른 일을 하는 중이면(쿠키 저장·수집) 그
  일이 끝난 뒤에 잇는다.
- **계산 중에는 탭을 옮기지 않는다**(`src/lib/extensionLink.ts`의 `arrivalStep` — 자동 추적의 탭 이동과 같은 규칙이다): 어느
  탭에서든 계산이 도는 동안 쿠키를 받으면 보던 탭에 머물고 `크롬 확장에서 쿠키를 받았다 — 계산이 끝나면 계정 탭으로 옮겨 계정을
  새로 받는다` 한 줄이 보인다. 계산이 끝나면 계정 탭으로 옮긴다. 그 전에 계정 탭을 직접 열면 곧바로 받는다. 계정 화면을 이미
  한 번 열어 둔 뒤라면 받기 자체는 계산 중에도 곧바로 시작한다(엔진 계산과 계정 수집은 서로 다른 자리에서 돈다) — 미루는 것은
  탭 이동뿐이다.

### 보안

세션 쿠키는 **계정 접근권**이다. 규칙은 §계정 받기 §보안 규칙과 같고, 이 경로에 더해진 것은 아래다. 코드의 규칙이고 테스트가
확인한다(`src-tauri/tests/extension_link.rs`, `extension_link.rs`의 단위 테스트, `tests/contract.test.ts` 「크롬 확장 연결(Rust)」,
`tests/ExtensionLink.test.ts`, `extension/tests/`).

- **루프백에만 묶인다.** 듣는 소켓은 `127.0.0.1:47615` 하나다(`TcpListener::bind(SocketAddrV4::new(Ipv4Addr::LOCALHOST, port))` —
  모든 주소 `0.0.0.0`이 아니다). 다른 PC에서는 닿을 수 없다. 통합 테스트가 수신부를 실제로 열어, 듣는 주소가 127.0.0.1이고
  이 PC의 **다른 주소(랜 주소)로는 같은 포트에 연결이 거절되는 것**을 본다. 받은 연결의 상대가 루프백인지도 한 번 더 본다.
  이 모듈은 밖으로 연결을 만들지 않는다(듣고, 들어온 연결에 답할 뿐 — 앱 전체에서 소켓 코드는 이 모듈 하나다).
- **켰을 때만 열린다.** 기본 꺼짐. 끄면 소켓이 닫혀 같은 주소로 연결이 거절된다. 앱이 끝날 때도 닫는다(종료 처리에서 닫고,
  프로세스가 죽으면 운영체제가 닫는다).
- **정해진 요청 하나만 받는다.** `POST /nikke-companion/v1/session`, `Content-Type: application/json`, 본문은 글자인 `code`와
  `cookie` 두 칸만 있는 JSON 객체. 요청 머리 8KiB·본문 32KiB까지, 연결 하나에 요청 하나, 3초 안에 다 오지 않으면 끊는다.
  그 밖은 거부한다: 다른 경로 404, 다른 방법 405, 다른 형식 415, 길이를 알리지 않으면 411, 너무 크면 413(본문을 읽지 않는다),
  모양이 다른 본문·겹친 헤더 400.
- **웹 페이지는 부르지 못한다.** ① 출처(`Origin`)가 `chrome-extension://<확장 ID 32자>`가 아니면 403 — 웹 페이지의 출처
  (`https://…`·`http://…`·`null`)와 출처 없는 요청은 연결 코드가 맞아도 거부한다. ② 어떤 답에도 다른 출처 허용 헤더
  (`Access-Control-Allow-*`)가 없다 — 브라우저가 다른 출처의 페이지를 대신해 보내는 사전 요청(OPTIONS)은 실패하고, 페이지는
  답을 읽지 못한다. ③ 사전 요청 없이 보낼 수 있는 「단순 요청」은 형식이 `application/json`이 아니라서 거부된다. ④ `Host`가
  `127.0.0.1:47615`가 아니면 403(다른 이름으로 이 주소를 가리키게 한 페이지를 막는다). 웹 페이지의 요청은 틀린 코드로 세지 않고
  화면에 알리지도 않는다 — 페이지가 요청을 쏟아부어 확장을 막거나 화면을 어지럽힐 수 없다.
- **응답과 로그에 쿠키가 없다.** 답은 정해진 낱말로만 만든다(`{"ok":true,"result":"received"}` / `{"ok":false,"reason":"…"}`
  — 사유는 `wrong_code`·`locked`·`not_logged_in`·`busy` 같은 낱말, 막혔을 때만 남은 초). 요청에 실려 온 글자는 답에 되돌아가지
  않는다. 본문을 읽다 난 오류의 문장도 버린다(값이 섞여 나올 수 있다). 확장이 보낸 것을 담는 Rust 타입은 `Debug`에서 값을 가리고
  직렬화할 수 없다. 이 모듈은 표준 출력·표준 오류에 아무것도 쓰지 않는다. 화면으로 가는 것(명령의 반환값과 `extension-link`
  이벤트)은 상태 여덟 칸뿐이다: 켜짐·듣는 중·주소·연결 코드·문제·받았다·마지막 요청(시각·종류·문장)·막힌 시간.
  **쿠키는 오버레이 화면을 지나가지도 않는다.** 통합 테스트가 가짜 쿠키로 모든 길(받기·코드 틀림·막힘·로그인 안 됨·형식 거부·
  수집 중·저장 실패·모양이 다른 요청에 쿠키를 실어 보내기)을 밟고, 답·상태·이벤트·`Debug` 출력·설정 파일과, 따로 띄운
  프로세스의 표준 출력·표준 오류에 그 쿠키가 없는 것을 본다.
- **쓰는 곳은 여전히 하나다.** 받은 헤더는 붙여넣기와 같은 함수(`account_sync::store_pasted_cookie` → `cookie::normalize_pasted`)
  를 거쳐 엔진의 `scraper/.session_cookie`에만 쓰인다. `game_token`·`game_openid`가 없으면 쓰지 않고 `not_logged_in`으로 답한다
  (확장이 먼저 걸러 보내지 않지만, 받는 쪽도 다시 본다). 코드가 맞기 전에는 쿠키를 저장하는 쪽에 넘기지 않는다.
- **확장**의 권한은 `cookies`와 호스트 권한 둘(`https://*.blablalink.com/*`, `http://127.0.0.1/*`)뿐이고, 백그라운드에서 돌지
  않으며, 쿠키를 저장하지 않고 127.0.0.1 말고는 보내지 않는다(`extension/README.md` §권한과 보안).

**막지 못하는 것.** 같은 PC에서 도는 다른 프로그램은 출처 헤더를 지어낼 수 있다 — 그래도 연결 코드가 있어야 하고, 그런 프로그램은
이 수신부가 없어도 브라우저의 쿠키 파일이나 엔진의 쿠키 파일을 읽을 수 있다. 연결 코드와 출처 확인은 **웹 페이지와 다른 PC**를
막는 장치다. 연결 코드가 틀린 요청을 일부러 다섯 번 보내면(같은 PC의 프로그램이나, 설치된 다른 확장이) 1분 동안 받기를 막을 수는
있다. 통신은 평문 HTTP지만 루프백을 벗어나지 않는다.

### 새 의존성

- `getrandom` 0.3 — 연결 코드를 운영체제의 난수로 만든다. 표준 라이브러리에는 예측할 수 없는 난수를 얻는 길이 없다. Tauri가
  이미 끌어오는 판이라 새로 받는 크레이트는 없다.
- 수신부는 **표준 라이브러리**(`std::net::TcpListener`)로 만들었다 — HTTP 서버 크레이트를 더하지 않았다. 받는 요청이 하나뿐이라
  요청 줄·헤더·`Content-Length` 본문만 직접 읽는다(청크 전송·연결 유지·TLS는 없다).
- capability에는 새 명령 넷만 더했다(`extension_link_status`·`extension_link_set`·`extension_link_new_code`·
  `extension_link_take_pending`). 화면이 정하는 것은 켜짐뿐이다 — 듣는 주소·포트·연결 코드는 정하지 못한다.

### 한계

- **크로뮴 계열 브라우저**(크롬·엣지·웨일·브레이브)만 된다 — 출처가 `chrome-extension://…`인 요청만 받는다. 파이어폭스는 안 된다.
  크롬 말고는 써 보지 않았다.
- **확장을 고치면 다시 로드해야 한다**(`chrome://extensions`의 ↻). 압축해제된 확장은 폴더를 가리킬 뿐이라 저장소를 옮기면 다시 불러온다.
- 포트는 **47615로 고정**이다(확장의 코드에 적혀 있다). 다른 프로그램이 쓰고 있으면 켜지지 않고
  `127.0.0.1:47615를 다른 프로그램이 쓰고 있다`고 알린다 — 스위치는 켜진 채로 남고, 그 프로그램을 끈 뒤 껐다 켜면 열린다.
- 연결은 순서대로 하나씩 받는다(요청 하나가 3초까지 붙들 수 있다). 사람이 단추를 누르는 용도라 문제가 되지 않는다.
- 받는 것은 그 브라우저 프로필에 로그인돼 있는 blablalink 계정 하나다. 어느 계정의 쿠키인지 오버레이는 구분하지 않는다 —
  이름 칸의 이름으로 저장한다.
- 쿠키가 만료됐으면 확장은 여전히 「받았다」까지 간다(쿠키가 있기는 하다) — 그 뒤의 수집이 `세션 만료`로 실패하고 계정 화면에
  안내가 보인다. 브라우저에서 blablalink를 한 번 열어 로그인 상태를 되살린 뒤 다시 누른다.
- **실제 크롬과 실제 오버레이 창으로는 한 번도 주고받아 보지 않았다**(§사람이 확인할 것). 확인하지 못한 가정: 확장의 요청에
  브라우저가 `Origin: chrome-extension://…`을 붙인다, 호스트 권한 `http://127.0.0.1/*`가 포트 47615에도 맞아 사전 요청 없이
  나간다, `chrome.cookies.getAll({url})`이 `game_token`·`game_openid`를 돌려준다(실제 쿠키의 도메인을 모른다).

### 테스트

브라우저도 확장도 띄우지 않는다. 쿠키는 지어낸 글자이고, 쿠키 파일은 임시 폴더의 가짜 엔진 폴더에만 쓰이며, 실제 포트(47615)와
앱의 설정 폴더는 건드리지 않는다(테스트는 빈 포트를 쓴다).

```bash
cargo test --manifest-path app/src-tauri/Cargo.toml --test extension_link   # 수신부를 실제로 열고 가짜 요청을 소켓으로 보낸다(몇 초. 평소 cargo test에도 들어 있다)
node --test extension/                                                      # 확장: 쿠키 목록 → 헤더, 보내기 흐름, manifest, 오버레이와의 계약
```

- `src-tauri/tests/extension_link.rs`(17건): 루프백 전용(다른 주소로는 거절), 기본 꺼짐·켜면 열림·끄면 닫힘·버리면 닫힘, 켜짐과
  코드의 기억(설정 파일에 그 둘뿐), 포트가 쓰이고 있을 때의 안내, 확장의 요청 → 쿠키 파일 한 곳에 한 줄 → 「받았다」 알림 →
  차례는 한 번, 방법·경로·형식·크기·모양이 다른 요청 거부, 멈춘 요청 끊기, 웹 페이지의 요청 거부(출처·사전 요청·단순 요청·

  요청은 쓰지 않음, 수집 중에는 쿠키를 바꾸지 않음, 저장 실패는 사유의 낱말만, **쿠키 비노출**(위 §보안), 함께 온 요청 여섯 개.
- `extension_link.rs`의 단위 테스트(16건): 코드의 글자·읽기·견주기·무작위, 틀린 횟수와 막힘(시간을 넣어 준다), 머리 읽기와
  가리기(경로·출처·방법·호스트·형식·크기 저마다), 본문 읽기, 코드가 맞기 전에는 저장하는 쪽에 가지 않음, 답에 허용 헤더가 없음.
- 프런트 `tests/ExtensionLink.test.ts`(23건, Rust 쪽은 가짜 — 이 길에는 쿠키가 화면에 오지 않으므로 테스트에도 쿠키가 없다):

- 프런트 `tests/contract.test.ts` 「크롬 확장 연결(Rust)」(8건)과 「(d) 네트워크」: 묶는 주소가 한 줄뿐이고 루프백임, 소켓 코드가

## 디자인 기반

UI 개편(데스크톱 앱 + 오버레이 — 기준 문서는 `docs/ui-redesign.md`)의 바탕이다: 디자인 토큰, 이미지를 읽는 명령, 공통 부품,
부품 모아 보기. **기존 화면은 아직 예전 모양 그대로다** — 새 구조로 옮기는 것은 다음 작업(P-027·P-028)이다.

### 토큰

`src/styles/tokens.css` — 어두운 테마의 색(배경·표면·글자·테두리), 강조색(보라 계열 하나), 속성 색 다섯(작열 빨강·풍압 초록·
철갑 주황·전격 보라·수냉 파랑), 상태 색(정상·추정·미확인·오류·검증용), 간격·모서리·글자 크기의 단계, 부품 크기. 값의 표는
`docs/ui-redesign.md` §5.

- 이름은 모두 `--nk-`로 시작한다. 이 파일은 **변수만** 정한다 — 불러와도 기존 화면의 모양은 바뀌지 않는다
  (기존 화면은 `src/style.css`의 예전 변수를 쓴다).
- **부품은 색·크기를 직접 적지 않고 토큰만 쓴다.** `tests/DesignTokens.test.ts`가 `src/ui/`의 모든 파일을 본다: 16진수·`rgb()`·
  색 이름·`px` 값이 없고, 쓰는 토큰이 모두 정의돼 있다.
- 속성 색은 `data-element="작열"`(엔진 카탈로그의 낱말 그대로)로, 상태 색은 `data-tone="estimate"`로 고른다 —
  그 요소 안에서 `--nk-el`·`--nk-tone`이 그 색이 된다. 낱말이 없으면 「모름」 색이다.

### 부품

`src/ui/` — 니케 타일(`NikkeTile` — 크기 `lg`·`sm`·`xs`), 보스 카드(`BossCard`), 속성 칩(`ElementChip`), 버스트 배지(`BurstBadge`),
아이콘(`GameIcon`), 딜 막대(`DamageBar`), 순위 줄(`RankRow`), 상태 알약(`StatusPill`), 진행 패널(`ProgressPanel`),
뼈대 화면(`SkeletonBlock`), 빈 상태(`EmptyState`), 접는 「자세히」(`DetailsFold`). 무엇을 그리고 어떤 상태가 있는지는
`docs/ui-redesign.md` §6.

- 부품은 보여 주기만 한다 — 계산하지 않고 결과 문서의 모양을 모른다. 대미지 표기는 `lib/format.ts`(루트의 `src/core/format.mjs`),
  남은 시간은 루트의 `src/core/eta.mjs`, 한 줄 요약은 루트의 `src/core/summary.mjs`가 만든다.
- 모르는 것은 「모름」으로 그린다: 초상화가 없으면 이름 첫 글자, 속성·버스트 단계를 모르면 「?」, 딜 비중을 모르면 「–」,
  총딜을 모르면 「계산 전」. 0이나 그럴듯한 값으로 채우지 않는다.
- 니케의 속성·버스트 단계·무기·기업은 `lib/nikkeInfo.ts`로 얻는다 — 이미 있는 `engine_catalog` 명령의 카탈로그에서 읽고,
  카탈로그에 없는 값은 `null`(「모름」)이다.

### 이미지가 어디서 오는가

화면에는 파일·네트워크 권한이 없다(capability에 새 명령 셋만 더했다 — 파일·네트워크 플러그인은 없다. CSP도 그대로다).
이미지는 Rust 명령이 **이 PC의 파일에서 읽어** base64로 넘기고(`src-tauri/src/assets.rs`), 화면은 `data:` 주소로 그린다
(`lib/images.ts` — 한 번 물은 것은 기억한다).

| 명령 | 읽는 조건 | 읽는 순서 | 없으면 |
|---|---|---|---|
| `nikke_portrait(name)` | 이름이 엔진 카탈로그에 있다 | 엔진 폴더 `image/<이름>.webp` → `data/assets/portraits/` | 이름 첫 글자 |
| `boss_image(id)` | id가 내장 보스 묶음(`data/intercept/anomaly.json`)에 있다 | `data/assets/bosses/` → `data/captures/bosses/<id>.png`(캡처에서 잘라 둔 조각) | 보스의 속성 색 |
| `game_icon(kind, key)` | 종류·값이 아이콘 표에 있다 | `data/assets/icons/<종류>/` → 엔진 폴더 `image/icon/`(파일 이름이 엔진 코드에서 확인된 속성·버스트·클래스만) | 직접 그린 도형·글자 |

- 화면이 넘기는 이름·id·종류는 **경로가 아니라 열쇠**다. 카탈로그·보스 묶음·아이콘 표에 없는 문자열은 파일을 건드리지 않고
  「없음」이 된다 — 화면이 넘긴 문자열로 임의의 파일을 읽을 수 없다(경로 탈출 테스트가 있다).
- 초상화의 파일 이름은 엔진의 `scraper/cdn_fetch.py`의 `safe_filename()` 규칙 그대로다(금지 글자 아홉 개 → `_`).
- **없는 이미지는 오류가 아니다** — `{found: false}`로 온다. 읽은 내용이 WebP·PNG가 아니거나 2MB를 넘어도 「없음」이다.
- 받아 둔 리소스(`data/assets/`)는 `node scripts/fetch-assets.mjs`(저장소 루트)가 받는다 — **사람이 실행한다**
  (`--list`로 무엇을 받는지 먼저 본다). 지금은 받을 것이 없다: 경로가 확인된 것은 초상화뿐이고 그것은 엔진 폴더에 이미 있다.
  아이콘·보스 이미지의 주소는 확인하지 못해 받지 않는다(`docs/ui-redesign.md` §8).

### 게임 이미지를 저장소에 넣지 않는 이유

게임 이미지와 아이콘은 SHIFT UP / Level Infinite의 권리물이다(`docs/spec.md` §7) — 이 저장소의 코드 라이선스와 별개이고,
저장소에 넣으면 그것을 다시 배포하는 일이 된다. 그래서:

- 받아 둔 리소스(`data/assets/`)와 캡처(`data/captures/`)는 gitignore다.
- 초상화와 일부 아이콘은 엔진 서브모듈(`vendor/nikke-calc/image/` — 남의 저장소)에 있는 것을 **읽기만** 한다.
- 테스트는 코드로 만든 가짜 이미지(머리 바이트만 WebP·PNG 꼴인 몇십 바이트)로만 한다. fixture에 게임 이미지가 없다.
- 설치된 게임 클라이언트의 파일은 건드리지 않는다(풀거나 복호화하지 않는다). 다른 팬 사이트의 이미지도 가져오지 않는다.

### 부품 모아 보기

모든 부품과 상태(이미지 있음/없음, 긴 이름, 계산 중, 빈 상태, 오류)를 한 화면에서 본다. **개발 실행에서만** 뜬다 —
빌드한 앱에는 그 화면의 코드가 들어가지 않는다(`main.ts`의 `import.meta.env.DEV` 갈래 — 빌드 결과에 없는 것을 확인했다).

```powershell
$env:VITE_UI_GALLERY = '1'; npm --prefix app run tauri dev    # 앱 창에서: 실제 초상화·보스 이미지가 보인다
npm --prefix app run dev                                      # 브라우저에서: 주소 뒤에 ?gallery (이미지 명령이 없어 전부 대체 그림)
```

여기의 숫자는 지어낸 보기 값이다(`src/ui/gallery/samples.ts`) — 화면 맨 위의 「검증용 데이터」 배지가 그렇게 밝힌다.

## 빌드

```bash
npm --prefix app run tauri build     # app/src-tauri/target/release/nikke-companion.exe
```

설치 파일은 만들지 않는다(`bundle.active: false`). 개인용이라 실행 파일 하나면 충분하고, 배포는 범위 밖이다.

`cargo build --manifest-path app/src-tauri/Cargo.toml`만 하면 개발용 실행 파일이 나온다. 이것은 화면을
개발 서버(`localhost:1420`)에서 읽으므로 서버 없이 실행하면 빈 창이 뜬다. 혼자 도는 실행 파일은 위 명령으로 만든다.

## 단축키 (전역)

| 단축키 | 동작 |
|---|---|
| `Alt+Shift+C` | 클릭 통과 켜기/끄기. 켜면 마우스 입력이 오버레이를 지나 아래 프로그램으로 간다 |
| `Alt+Shift+O` | 오버레이 숨기기/보이기 |
| `Alt+Shift+S` | 지금 게임 화면을 PNG로 저장(§게임 창·화면 캡처). 결과는 게임 창 칸에 보인다 |

- 시작할 때는 보이고 조작할 수 있는 상태다(주 모니터 작업 영역의 오른쪽 위).
- 클릭 통과 중에는 창을 조작할 수 없다. 주황색 줄무늬 띠와 테두리로 표시되고, `Alt+Shift+C`로 되돌린다.
- 숨긴 동안에는 `Alt+Shift+C`를 무시한다. 다시 보이면 숨기기 전의 클릭 통과 상태 그대로다.
- **단축키는 키보드 포커스를 바꾸지 않는다**(§포커스). `Alt+Shift+O`로 다시 보여도 오버레이가 활성화되지 않는다 —
  오버레이의 입력란에 글자를 넣으려면 오버레이를 한 번 클릭한다.
- 다른 프로그램이 같은 단축키를 쓰고 있어 등록하지 못하면 화면에 경고가 뜬다.
- 창 옮기기: 맨 위 제목 줄을 끈다. 끝내기: 제목 줄의 `×`.

### 포커스 — 보일 때 활성화하지 않는다

단축키는 게임을 하는 도중에 눌린다. 오버레이가 다시 보이면서 활성화되면 게임이 키보드 포커스를 잃어 입력이 끊긴다.

- 규칙(`src-tauri/src/overlay_state.rs`): 전환이 창에 시키는 보임 변화는 `ShowWithoutActivating`(활성화 없이 보이기)과
  `Hide` 둘뿐이다. 활성화하며 보이는 변화는 없다. 클릭 통과 전환은 보임을 바꾸지 않는다(창 스타일만 바꾼다).
- 창에 반영(`src-tauri/src/overlay_win32.rs`): Windows에서는 Win32의 활성화 없는 표시 `ShowWindowAsync(SW_SHOWNA)`로
  보이고 `SW_HIDE`로 숨긴다. 창 라이브러리(tao)의 `show()`는 `SW_SHOW`라서 창을 활성화한다 — 그래서 쓰지 않는다.
  활성화(전경으로 가져오기)·포커스 주기 호출은 없다(`tests/contract.test.ts`가 확인한다). Windows가 아니면 창 라이브러리의
  `show()`·`hide()`를 그대로 쓴다(기존 동작). 게임에 덮인 오버레이를 다시 올리는 것도 활성화 없이 한다(§게임 위에 머물기).
- 시작할 때 한 번은 `window.show()`로 보인다(사용자가 방금 띄운 창이라 활성화돼도 된다).
- 이 모듈이 건드리는 창은 오버레이 창 하나뿐이다. 게임 창은 찾지도 받지도 않는다.
- 알아 둘 것: 시작 뒤에는 보임/숨김을 Win32로만 바꾸므로 창 라이브러리는 이 창이 계속 보인다고 안다. **숨긴 동안에**
  창 스타일을 바꾸는 호출(클릭 통과 전환 등)을 부르면 창이 다시 나타날 수 있다 — 지금은 규칙이 숨긴 동안의 클릭 통과
  전환을 무시하므로 일어나지 않는다. 보임/숨김에 `window.show()`·`window.hide()`를 섞어 쓰지 말 것.
- **확인하지 못한 것**: 창 라이브러리의 소스는 이 작업에서 읽지 못했다(위의 "`SW_SHOW`라서 활성화한다"와 "스타일을 다시
  입힌다"는 P-009 때의 관찰과 기억이다). 실제 창에서 단축키를 눌러 본 것도 아니다 — 숨겼다 다시 보인 창이 제대로
  그려지는지, 게임 입력이 끊기지 않는지는 사람이 본다(§사람이 확인할 것).

### 파일 고르기 창

`고르기`는 Rust 명령 `pick_json_file`이 연다. 대화 상자의 **부모(소유자)는 오버레이 창**이다: 명령이 받은 오버레이 창의
핸들을 `overlay_win32::dialog_parent`로 꺼내 그대로 넘긴다. Windows는 소유된 창을 소유자보다 언제나 위에 두므로, 항상 위인
오버레이 뒤에 대화 상자가 가려지지 않는다. 창 핸들을 얻지 못하면 부모 없이 띄우지 않고 오류로 알린다(경로는 직접 넣으면 된다).
대화 상자가 떠 있는 동안 오버레이는 조작할 수 없다(모달). **실제로 띄워 본 것은 아니다** — 사람이 확인한다.

## 중복 실행 방지

오버레이는 한 번만 뜬다(P-021). 이미 떠 있는데 한 번 더 실행하면:

- **두 번째 실행은 창을 만들지 않고 조용히 끝난다**(종료 코드 0). 예전에는 창이 하나 더 뜨고 전역 단축키 등록 실패 경고가 보였다.
- **떠 있던 오버레이가 숨겨져 있었다면 다시 보인다 — 활성화 없이**(§포커스와 같은 길: `SW_SHOWNA`). 게임을 하다가 바로 가기를
  눌렀어도 게임의 키보드 포커스는 그대로다. 보이고 있었다면 아무것도 바뀌지 않는다. 클릭 통과 여부도 그대로다.
- 두 번째 실행에 준 인자(결과 파일 경로)는 쓰지 않는다 — 떠 있는 창에서 직접 불러온다.

만든 방법: Tauri의 `tauri-plugin-single-instance`(2.x)를 **맨 먼저** 등록한다(`src-tauri/src/lib.rs`의 `run`). 이 플러그인이
앱 식별자(`local.nikke-companion.overlay`)로 이름 붙인 뮤텍스를 쥐고, 두 번째 실행은 플러그인 초기화에서(창을 만들고 단축키를
등록하기 전에) 떠 있는 쪽에 알린 뒤 끝난다. 떠 있는 쪽에서 불리는 함수가 `reveal_overlay`다: 규칙(`overlay_state.rs`의
`OverlayAction::Show` — 숨겨져 있으면 보임, 보이면 그대로)으로 상태를 바꾸고, 창에는 활성화 없는 보이기를 건다. 논리 상태가
"보임"이어도 창에 한 번 더 요청한다(이미 보이는 창에는 아무 일도 없다). 화면(웹뷰)에서 부르는 것이 없어 **capability에 더한
권한은 없다.** 이 앱의 두 실행끼리만 신호를 주고받는다(게임과 무관하다).

```bash
cargo test --manifest-path app/src-tauri/Cargo.toml --test live_single_instance -- --ignored --nocapture
```

`tests/live_single_instance.rs`가 개발용 실행 파일을 실제로 세 번 띄워 확인한다(화면이 켜진 데스크톱과 WebView2가 필요해서
`#[ignore]`. 10초쯤 화면 오른쪽 위에 오버레이 창이 떴다 사라지고, 그동안 전역 단축키가 잠깐 등록된다. **이미 떠 있는 오버레이는
끄고 돌린다** — 아니면 테스트의 첫 실행이 곧바로 끝나 실패한다):

- 첫 실행은 오버레이 창 하나를 띄운다. 두 번째 실행은 종료 코드 0으로 끝나고(잰 값 0.1초) 그 프로세스가 오버레이 창을 가진
  적이 없으며, 떠 있던 창은 그대로 하나다.
- 떠 있는 창을 숨긴 뒤(테스트가 자기가 띄운 오버레이 창에 `SW_HIDE`) 한 번 더 실행하면 그 창이 다시 보이고, **전경 창이 되지
  않는다**.

돌려 본 결과(2026-11-12): 통과. 규칙은 단위 테스트가 본다(`overlay_state.rs` — 숨겨져 있으면 활성화 없이 보임, 보이면 변화 없음).

한계: 단축키(`Alt+Shift+O`)로 숨긴 상태에서의 두 번째 실행은 자동 테스트로 보지 못했다(테스트는 창을 밖에서 숨긴다 — 앱 안의
상태는 "보임" 그대로다. 규칙은 단위 테스트로, 창에 거는 요청은 이 통합 테스트로 따로 본 것이다). 관리자 권한으로 띄운 오버레이와
일반 권한으로 띄운 두 번째 실행 사이에서는 Windows가 신호를 막을 수 있다 — 그때도 두 번째 실행은 끝나지만 숨겨진 창이 다시
보이지 않을 수 있다(확인하지 않았다). 플러그인의 소스는 이 작업에서 읽지 못했다(위의 "뮤텍스"·"초기화에서 끝난다"는 플러그인
문서와 기억이고, 창을 만들지 않고 끝나는 것은 통합 테스트로 확인했다).

```bash
npm --prefix app run fixture                  # 넷 다 (몇 분 — 시뮬 결과 캐시를 쓰지 않는다)
npm --prefix app run fixture -- tier growth   # 고른 것만: compare · intercept · growth · tier
```

셸 문자열 대신 인자 배열로 넘긴다):

## 사람이 확인할 것 (아직 확인하지 않았다)

디자인 기반(P-026) — **부품의 실제 모습을 눈으로 보지 못했다.** 자동 실행 세션은 창도 브라우저도 띄울 수 없어 컴포넌트 테스트
(구조·글자·상태)와 CSS를 읽는 것으로만 확인했다. 리소스도 실제로 받지 않았다(받기는 가짜 서버로만 확인했다):

- 부품 모아 보기(`$env:VITE_UI_GALLERY = '1'; npm --prefix app run tauri dev`)에서 실제 초상화와 보스 이미지가 보이고 어색하지
  않은지: 큰 타일에서 얼굴이 잘리지 않는지(위쪽 기준으로 자른다), 작은 타일 다섯이 한 줄에 들어가는지, 긴 이름이 말줄임되는지,
  약점 속성 테두리가 눈에 띄는지, 전격(보라)과 강조색(보라)이 헷갈리지 않는지, 글자 크기(10~13px)가 읽히는지.
- 엔진 폴더의 아이콘(속성·버스트·클래스)이 어두운 바탕에서 보이는지, 작은 크기에서 알아볼 수 있는지. 직접 그린 대체 도형
  (모아 보기의 「직접 그린 도형」 줄)이 쓸 만한지.
- `node scripts/fetch-assets.mjs --list`로 받을 것을 확인한 뒤(지금은 0개일 것이다) 받을 것이 있을 때 `--run`으로 받고,
  받은 이미지가 화면에 맞게 나오는지. `data/assets/icons/…`에 아이콘을 직접 넣으면 그것이 엔진 폴더의 것보다 먼저 쓰이는지.
- 기존 화면(탭 다섯)이 예전과 똑같이 보이는지 — 토큰 파일을 불러오게 됐지만 변수만 정하므로 달라지면 안 된다.

오버레이 견고화(P-024) — **실제 게임 위에서도, 실제 오버레이 창에서도 보지 않았다.** 창 올리기는 테스트가 띄운 창으로, 종료 시
정리는 가짜 엔진을 띄운 테스트 실행 파일로, 계산 중 탭 이동은 가짜 IPC 테스트로만 확인했다:

- 붙이기를 켠 채 게임을 누르고 옮겨도 오버레이가 게임 위에 보이는지(§게임 위에 머물기). 붙이기를 끈 채 오버레이를 게임 위에 올려
  두었을 때도 같은지. 니케는 관리자 권한으로 돈다 — 일반 권한으로 띄운 오버레이도 다시 올라오는지.
- 오버레이가 다시 올라올 때 게임 조작(누르기·끌기·키 입력)이 끊기지 않는지, 오버레이가 깜박이지 않는지(게임이 스스로 맨 위로
  올라오는 창이면 0.1초마다 자리를 바꿀 수 있다). 게임을 누른 직후 오버레이가 사라졌다 나타나는 것이 눈에 거슬리는지.
- 게임 창을 최소화하면 오버레이가 그 자리에 머무는지(화면 밖으로 사라지지 않는지), 다시 띄우면 붙는지. 게임을 다른 모니터로
  옮기면 따라가는지(배율이 다른 모니터 포함). 게임을 껐다 켜면 다시 붙는지.
- 전체 화면(테두리 없는 창·전용 전체 화면)에서도 오버레이가 보이는지.
- 계산 중에(추천·요격전·성장) 오버레이를 `×`로 끄면 작업 관리자에 python 프로세스가 남지 않는지. 계정 수집 중에 꺼도 같은지.
  작업 관리자에서 오버레이를 「작업 끝내기」로 끝내도 같은지(§종료 시 정리).
- 계산을 돌려 놓고 다른 화면을 보는 동안 게임에서 이상 개체 보스를 열면: 탭이 그대로이고 `계산이 끝나면 요격전 탭으로 옮긴다`
  한 줄이 보이는지(440px에서 넘치지 않는지), 계산이 끝나면 요격전 탭으로 넘어가는지(§자동 추적).

크롬 확장으로 계정 받기(P-025) — **확장을 실제 크롬에 설치해 본 적이 없고, 실제 오버레이 창과 주고받아 본 적도 없다.** 수신부는
테스트가 보낸 가짜 요청으로, 확장은 Node에서 가짜 쿠키·가짜 요청으로, 화면 흐름은 가짜 IPC 테스트로만 확인했다(에이전트는
사용자의 크롬에 확장을 설치하거나 실제 blablalink에 로그인하지 않는다):

- 확장이 오류 없이 로드되는지(`chrome://extensions`에 오류 단추가 없는지), 팝업이 제대로 보이는지.
- 계정 탭에서 「크롬 확장 연결」을 켜면 `켜짐 · 127.0.0.1:47615에서 듣는 중`과 연결 코드가 보이는지. Windows 방화벽이 묻는 창이
  뜨는지(루프백에만 묶어 뜨지 않을 것으로 보지만 확인하지 못했다).
- 연결 코드를 확장에 넣고, blablalink에 로그인된 상태에서 「오버레이로 보내기」 한 번으로 계정이 끝까지 받아지는지(계정 탭이
  열리고, 받는 중 → 변환·저장 → 다른 화면의 계정 칸).
- blablalink에 로그인돼 있지 않을 때 `blablalink에 로그인돼 있지 않다`, 오버레이가 꺼져 있거나 스위치가 꺼져 있을 때
  `오버레이가 꺼져 있다`, 코드를 틀리게 넣었을 때 `연결 코드가 틀리다`(다섯 번이면 `잠시 막았다`)가 팝업에 맞게 나오는지,
  계정 화면의 「마지막 요청」 줄도 맞는지.
- 확인하지 못한 가정이 맞는지 — 틀리면 팝업에 `오버레이가 아닌 답이 왔다 (origin)`처럼 사유가 보인다: 브라우저가 확장의 요청에
  `Origin: chrome-extension://…`을 붙이는지, 사전 요청(OPTIONS) 없이 보내는지, `chrome.cookies.getAll`이 `game_token`·
  `game_openid`를 돌려주는지(실제 쿠키의 도메인·경로를 모른다).
- 켜 둔 채 오버레이를 껐다 켜면 계정 탭을 열지 않아도 확장의 단추가 통하는지. 끄면 `오버레이가 꺼져 있다`가 나오는지.
- 계산을 돌려 놓고 확장의 단추를 누르면 탭이 그대로이고 한 줄 안내가 보이는지, 계산이 끝나면 계정 탭으로 넘어가 받는지.
- 방법 1 칸(스위치·코드·설치 순서 여섯 줄)이 440px에서 넘치지 않고 읽히는지.
- 엣지 등 다른 크로뮴 계열 브라우저에서도 되는지(크롬만 염두에 두고 만들었다).

계정 받기(P-022) — **실제 쿠키·실제 수집·실제 로그인은 한 번도 해 보지 않았다**(자동 테스트는 지어낸 쿠키·가짜 스크립트·샘플
프로필로만 한다. 로그인 창은 임시 세션으로 첫 페이지가 뜨는 것까지만 봤다). 계정 탭의 실제 모습도 창에서 보지 못했다:

- 실제 쿠키를 붙여넣고 「계정 새로 받기」로 계정 파일이 만들어지는지. 스크립트의 줄이 오는 대로 보이는지, 경고가 빠짐없이 보이는지.
- 쿠키가 만료됐을 때 안내가 맞게 나오는지(`세션 만료` — 실제 만료가 `game not login`으로 오는지, `캐릭터를 못 받았다`로 오는지 모른다).
- 로그인 창에서 실제로 로그인하고 「쿠키 가져오기」 → 「계정 새로 받기」가 되는지. 로그인한 뒤의 쿠키에 `game_token`·`game_openid`가
  `api.blablalink.com` 요청에 실리는 도메인으로 있는지(아니면 「아직 로그인되지 않았다」가 계속 나온다 — 그때는 붙여넣기).
- 로그인 창에서 로그인이 막히는 로그인 방식이 있는지(구글 등). 로그인 제공자가 새 창(팝업)을 띄울 때 그 창이 제대로 뜨고 닫히는지.
  막히면 붙여넣기로 되는지.
- 「로그인 세션 지우기」 뒤에 로그인 창을 다시 열면 로그인 전 상태인지.
- 계정 탭이 440px에서 넘치지 않고 읽히는지(탭 다섯 개가 한 줄에 들어가는지, 긴 경로·긴 경고 줄의 줄바꿈, 수집 줄 상자의 스크롤).
- 받은 계정으로 요격전 추천을 돌린 수치가 인게임 기록과 맞는지.

- 앱에서 샘플 계정으로 추천을 실행해 순위가 보이는지, `고르기` 창이 오버레이 위에 뜨는지.
- 실제 계정 파일로 실행한 수치가 인게임 기록과 맞는지.

- 실제 니케 PC판 위에서 오버레이가 보이는지(창 모드·전체 화면). 전체 화면 전용 모드에서는 가려질 수 있다.
- 클릭 통과 상태에서 창 아래 프로그램이 클릭되고 게임 입력을 방해하지 않는지.
- 게임을 하다가 `Alt+Shift+O`로 오버레이를 숨겼다 다시 보여도 게임 입력이 끊기지 않는지(P-016에서 활성화 없는 표시로
  바꿨다 — §포커스). 다시 보인 오버레이가 제대로 그려지는지, 숨긴 동안 `Alt+Shift+C`를 눌러도 나타나지 않는지도 함께 본다.
- `Alt+Shift+C`(클릭 통과 전환)가 게임의 키보드 포커스를 바꾸지 않는지.
- `고르기` 창이 오버레이 앞에 뜨는지(P-016에서 부모 창을 명시적으로 넘기게 했다 — §파일 고르기 창).
- 추천 실행 중에 `중단`을 누르면 곧바로 `중단됨`이 보이고 작업 관리자에 python이 남지 않는지(§계산 중단).
- Alt+Tab·창 이동·크기 변경 뒤에도 단축키와 표시가 맞는지.

게임 창·화면 캡처(P-011):

- 오버레이에서 `Alt+Shift+S`로 저장한 캡처가 실제 게임 화면과 같은지(단축키는 눌러 보지 못했다).
- 붙이기를 켠 상태에서 게임 창을 옮기거나 크기를 바꾸면 오버레이가 따라오는지(자동 테스트는 게임 창을 움직일 수 없다).
- 전체 화면(테두리 없는 창·전용 전체 화면)에서 캡처가 되는지.
- 캡처하는 순간 게임 창 둘레에 노란 테두리가 보이는지, 게임이 끊기지 않는지.

요격전·성장 비교·티어 화면(P-017) — **실제 창에서는 하나도 보지 않았다.** 가짜 IPC 테스트(화면의 글자와 구조)까지만 확인했고,
폭·줄바꿈·색은 브라우저로 그려 보지 못했다(CSS를 읽어 넘칠 곳을 점검한 것이 전부다):

- 오버레이(기본 440px)에서 요격전·성장·티어 화면이 넘치지 않고 읽히는지: 탭(지금은 다섯 개)이 한 줄에 들어가는지, 보스 단추 다섯 개의
  줄바꿈, 멤버별 딜 표(이름이 긴 니케 + `약점` 표시), 티어 줄(이름·버스트·점수·상태 표시, `미지원 효과 있음`이 붙었을 때).
- 요격전: 결과가 있을 때 창을 스크롤하지 않고 보스 이름·약점·1위 편성 5명이 보이는지(오버레이 상태·게임 창 칸·탭·접힌 입력 칸
  아래에 들어가야 한다). 실제 이상 개체 요격전 화면 옆에서 보스를 골라 가며 편성할 수 있는지.
- 티어: 스크롤해도 임시 규칙 문구가 맨 위에 붙어 있는지, 전원 계산 결과(209명)를 불러와도 느리지 않은지.
- 앱을 껐다 켰을 때 요격전의 마지막 결과와 보스가 실제로 다시 보이는지(웹뷰 저장소 — 테스트 환경의 localStorage로만 확인했다).
- 요격전 추천을 기본 예산(300건)으로 실제 엔진에서 돌렸을 때 진행 표시가 보스마다 넘어가는지, 그동안 다른 탭의 실행 단추가
  막히는지.

화면 인식(P-019):

- 실제 게임에서 이상 개체 요격전의 보스를 넘겨 가며 `nikke-capture --recognize-live`가 맞는 보스를 말하는지(선택 화면·편성 화면 둘 다).
  보스를 넘기는 도중에 찍히면 `unknown`이 나오는지, 틀린 보스가 나오는 일은 없는지.
- 다른 창 크기·전체 화면에서도 인식되는지(기준값은 창 모드 1881×1058 캡처에서 쟀다 — 다시 샘플링한 이미지로만 확인했다).

자동 추적·중복 실행 방지(P-021) — **실제 창에서는 스위치를 켜 보지 못했고, 이상 개체 화면을 띄운 채로도 돌려 보지 못했다**:

- 요격전 탭에서 `자동 추적`을 켜고 게임에서 이상 개체 보스를 넘기면 오버레이가 2~3초 안에 그 보스의 추천으로 바뀌는지
  (선택 화면·편성 화면 둘 다). 다른 탭을 보고 있었다면 요격전 탭으로 옮겨지는지. 상태 줄과 `읽음` 시각이 갱신되는지.
- 보스를 넘기는 도중·팝업·전투 화면에서 엉뚱한 보스로 바뀌지 않는지, 손으로 고른 보스가 자꾸 되돌아가지 않는지
  (`unknown`·`other`가 실제로 어떻게 나오는지에 달렸다 — §자동 추적 §언제 보스를 바꾸는가).
- 자동 추적을 켠 채 게임을 해도 끊김이 느껴지지 않는지. 추적 칸의 `캡처 1회 …ms`가 실제 게임 창에서 얼마로 나오는지
  (자기 창으로는 약 20ms였다 — 게임 창으로는 재지 못했다).
- 캡처하는 순간마다(2초에 한 번) 게임 창 둘레에 노란 테두리가 깜박이지 않는지.
- 게임을 껐다 켜거나 최소화했다 다시 띄우면 상태가 `게임 없음`/`게임 창 최소화`로 바뀌었다가 스스로 이어지는지.
- 오버레이를 두 번 실행해도 창이 하나인지, `Alt+Shift+O`로 숨긴 뒤 한 번 더 실행하면 다시 보이는지(게임 입력이 끊기지 않는지).
- 게임 창을 띄운 뒤 P-011의 `live_game` 5건과 `live_track`의 게임 창 측정이 통과하는지(이 작업에서 캡처 코드가 장치와
  캡처 대상을 다시 쓰게 바뀌었다 — 자기 창 테스트는 통과했다).
